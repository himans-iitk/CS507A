\title{What We Tell the Agent but Not the Newcomer}
\subtitle{Mining Agent Context Files for Gaps in Human Onboarding Documentation}

\author{Himanshu Mishra}

\begin{abstract}
AI coding agents such as Claude Code, OpenAI Codex and GitHub Copilot read a context file at the
start of every session. This file (\texttt{CLAUDE.md}, \texttt{AGENTS.md} or
\texttt{copilot-instructions.md}) tells the agent how to build, test and change the project. New
human contributors need the same information, but they read the README and CONTRIBUTING files
instead. We asked how much of what projects tell their agents they also tell people. We took
\nSampleRepos{} GitHub repositories (\nPerAgent{} for each type of agent file) that have a README
and a CONTRIBUTING file, and compared the three documents at the same commit. We read
\nQueued{} sections of the agent files and checked whether the human documents contain the same
knowledge. On average, \agentOnlyOverall{} of what a repository's agent file says appears only
there, and only \sharedOverall{} is fully available to people. Most of the missing knowledge is
about how to work on the project: \needGroupTopShare{} of it concerns processes and practices, such
as the development workflow and setting up the environment. Newcomers often struggle with exactly
these topics. A simple TF-IDF text matcher finds the missing sections with an F1 score of
\detectorFOne{} (recall \detectorRecall) on repositories it was not tuned on. Agent files are
therefore a ready source of material for better contributor documentation. We share our data,
codebook, labels, pipeline and detector.
\end{abstract}

\section{Introduction}
%======================================================================

Joining a software project is hard. A newcomer has to learn how the code is organised, how to set
up a working environment, which commands build and test the project, and which unwritten rules
apply to a change~\cite{sim1998rampup,begel2008novice,dagenais2010landscape}. In open source there
is rarely a mentor to ask. Many newcomers give up before their first contribution, and the reasons
they give most often include not knowing the project's process, failing to set up the
environment, and getting lost in the code~\cite{steinmacher2015barriers,steinmacher2015social}.
Projects try to help with documentation: a README that says what the project is, and a
CONTRIBUTING file that says how to work on it~\cite{prana2019readme,steinmacher2019letmein}. Yet
many CONTRIBUTING files leave out several of the barriers that newcomers
face~\cite{fronchetti2023contributing}.

Since 2025, many projects also write documentation for a different kind of newcomer. AI coding
agents such as Claude Code, OpenAI Codex and GitHub Copilot read a \emph{context file} at the
start of every session. Depending on the agent, the file is called \texttt{CLAUDE.md},
\texttt{AGENTS.md} or \path{.github/copilot-instructions.md}~\cite{chatlatanagulchai2026agentreadmes,mohsenimofidi2026context}.
An agent arrives in much the same position as a new human contributor. It knows the programming
language, but not the project. So maintainers tell it the same things: how to build and test, how
the code is organised, which conventions to follow and what not to touch. Early work suggests that
these files help agents most when they contain this kind of practical knowledge about the
project~\cite{gloaguen2026agentsmd}.

This leads to a simple question. Suppose a maintainer writes ``run \texttt{make verify} before
committing; never edit \texttt{src/gen/}'' in \texttt{CLAUDE.md}. Is that rule also in
\texttt{CONTRIBUTING.md}, or does the file for people still just say ``pull requests welcome''? If
agent files often contain knowledge that the human documents lack, then projects are onboarding
their agents better than their people. It would also mean that the agent file is a ready source
for improving the human documents. Earlier studies looked at agent files on their
own~\cite{chatlatanagulchai2026agentreadmes,mohsenimofidi2026context} and at onboarding
documents on their own~\cite{prana2019readme,fronchetti2023contributing}. As far as we know, no
one has compared the two inside the same repository. We do this, and ask three research
questions:

\begin{itemize}
\item \textbf{RQ1:} How much of the knowledge in agent files is missing from the README and
CONTRIBUTING of the same repository?
\item \textbf{RQ2:} Which newcomer needs and barriers does this missing knowledge relate to?
\item \textbf{RQ3:} Can we find this missing knowledge automatically?
\end{itemize}

We start from the Agent READMEs dataset~\cite{chatlatanagulchai2026agentreadmes}. For each agent
file, we find the commit at which it had the content stored in the dataset, and we take the README
and CONTRIBUTING from that same commit. We sample \nSampleRepos{} repositories, \nPerAgent{} for
each type of agent file, and split all documents at their headings into \nUnits{} sections. We
then label \nQueued{} agent file sections by hand. For each one we record its topic, using the
categories of an earlier study of agent files~\cite{chatlatanagulchai2026agentreadmes}; whether the
human documents cover it; and, if they do not, which newcomer need it serves~\cite{dagenais2010landscape}
and which barrier it would ease~\cite{steinmacher2015barriers}. Finally, we test simple text
matchers that predict the coverage label from the documents alone.

\begin{tcolorbox}[colback=black!3,colframe=black!35,boxrule=0.4pt,arc=1pt,left=4pt,right=4pt,top=3pt,bottom=3pt]
\small\textbf{Key findings.}
\begin{itemize}\setlength{\itemsep}{1pt}\setlength{\topsep}{2pt}\setlength{\leftmargin}{1em}
\item \textbf{RQ1:} On average, \agentOnlyOverall{} of what an agent file says is not in the README
or CONTRIBUTING, and \anyGapOverall{} is missing or only partly there. \repoAnyAgentOnlyShare{} of
repositories have at least some of this agent-only knowledge. Instructions about \catHighOne,
\catHighTwo{} and \catHighThree{} are most often agent-only; \catLow{} instructions are least often
(\catLowShare).
\item \textbf{RQ2:} \needGroupTopShare{} of the missing knowledge serves \emph{\needGroupTop}
needs. It would most often help with the barrier \emph{\barrierTopOne}.
\item \textbf{RQ3:} A TF-IDF matcher finds agent-only sections with F1 \detectorFOne{} (recall
\detectorRecall). Sentence embeddings do not do better.
\end{itemize}
\end{tcolorbox}

\paragraph{Contributions.} This paper makes four contributions. (1)~It is the first comparison of
agent files with human onboarding documents inside the same repository, section by section, for
three types of agent file. (2)~It describes what the missing knowledge is, using established
models of newcomer needs and barriers. (3)~It provides a gap detector, \texttt{gapcheck}, and tests
it on repositories that were not used to tune it. (4)~It comes with a replication package: the
documents, the codebook, \nCodedUnits{} labels together with a record of how each was made, and a
pipeline that rebuilds every number, table and figure in this paper with a single command.

Section~\ref{sec:related} covers related work and Section~\ref{sec:method} our method.
Section~\ref{sec:results} reports the results, and Section~\ref{sec:discussion} discusses what
they mean. Section~\ref{sec:limitations} lists the limitations, and Section~\ref{sec:conclusion}
concludes.

\section{Related Work}\label{sec:related}
%======================================================================

\subsection{Coding agents and their context files}

Large language models are now used across software engineering~\cite{hou2024llm4se}. Coding
agents go beyond completing code. They explore a repository, run commands and submit changes by
themselves. Benchmarks such as SWE-bench test how well they fix real GitHub
issues~\cite{jimenez2024swebench}, and the design of the tools an agent can use has a large effect
on its success~\cite{yang2024sweagent}. Developers also report that AI assistants often miss their
requirements and are hard to steer~\cite{liang2024usability}. Context files are one response to
this. They are Markdown files, loaded into every session, in which maintainers describe the
project for the agent.

Chatlatanagulchai et al.\ collected \nPackageFiles{} such files from GitHub, grouped their
instructions into 16 categories, and found that the files are hard to
read~\cite{chatlatanagulchai2026agentreadmes}. We reuse their dataset and their categories.
Mohsenimofidi et al.\ studied how open source projects prepare the context they give AI
agents~\cite{mohsenimofidi2026context}. Gloaguen et al.\ tested whether \texttt{AGENTS.md} files
help coding agents, and found that they help most when they describe practices specific to the
project~\cite{gloaguen2026agentsmd}. All three studies look at the agent file alone. We look at how
it relates to the documents that the same project writes for people.

\subsection{Newcomer onboarding}

Getting new members up to speed has long been difficult. Sim and Holt described how new
developers, whom they called ``software immigrants'', settle into a project~\cite{sim1998rampup}.
Begel and Simon followed new hires who had to learn their team's tools and processes before they
could contribute~\cite{begel2008novice}, and Ko et al.\ listed the kinds of information that
developers in teams look for~\cite{ko2007information}. Dagenais et al.\ described the
\emph{landscape} that a newcomer has to learn~\cite{dagenais2010landscape}. It includes the product
(its architecture, design, technologies and domain), the processes and practices (how development
and tasks are done, the environment and tools, and configuration management), the team, the
documentation, and the wider context. We use these features to describe which needs the agent-only
knowledge serves.

For open source, Steinmacher et al.\ collected the barriers that newcomers face. These include
problems with finding their way, with the newcomers' own background, with documentation, and with
technical hurdles~\cite{steinmacher2015barriers,steinmacher2015social}. The same group built a
portal that lowered these barriers~\cite{steinmacher2016portal} and wrote onboarding guidelines for
maintainers~\cite{steinmacher2019letmein}. Santos et al.\ review the tools proposed since
then~\cite{santos2024onboarding}. Other work helps newcomers find a first task, for example
through ``good first issues''~\cite{tan2020goodfirst}. The study closest to ours is by Fronchetti et
al. They checked CONTRIBUTING files against the barrier model and found that most projects leave
several barriers unaddressed~\cite{fronchetti2023contributing}. We use the same barrier model, but
we apply it to knowledge that a project has already written down, only for its agent.

\subsection{Developer documentation}

Developers depend on documentation, but they often find it incomplete or out of
date~\cite{lethbridge2003documentation,aghajani2019issues,aghajani2020practitioners}. Poor
documentation is one of the main obstacles to learning an API~\cite{robillard2009apis}. Prana et
al.\ classified what GitHub READMEs contain. READMEs mostly say what a project is and how to use
it, and less often how to contribute~\cite{prana2019readme}. Elazhary et al.\ found that in many
projects the actual contribution process does not match what the CONTRIBUTING guidelines
say~\cite{elazhary2019guidelines}. Documentation can also be improved with material from
elsewhere, for example by adding insights from Stack Overflow to API
documentation~\cite{treude2016augmenting}. Our study points to a new source of material that
already sits inside the repository.

\subsection{Matching documents and labelling with LLMs}

Deciding whether one text covers another is an old information retrieval problem in software
engineering. Traceability research links documentation to code with TF-IDF and vector space
models~\cite{antoniol2002traceability,salton1988termweighting} or with latent semantic
indexing~\cite{marcus2003lsi}. Today, sentence embeddings are the usual way to measure how similar
two texts are~\cite{reimers2019sbert}. Our detector compares both approaches on a new task:
matching agent instructions to sections of human documentation.

Large language models (LLMs) are also used more and more to label text. On some tasks they match
or beat crowd workers~\cite{gilardi2023chatgpt}. In software engineering they can take over part
of the human labelling effort, but not all of it, and agreement between different models helps
show which tasks are suitable~\cite{ahmed2025llmannotation}. LLMs are also used to judge the output
of other models~\cite{zheng2023judge}. We used an LLM in two ways: to draft labels that a person
then reviewed, and as an independent second annotator. We report both uses and what they mean for
the trustworthiness of our results.

\subsection{Data and the snapshot commit}

We build on the Agent READMEs dataset~\cite{chatlatanagulchai2026agentreadmes}. It contains
\nPackageFiles{} agent files from \nPackageRepos{} GitHub repositories: \texttt{CLAUDE.md} and
\texttt{AGENTS.md} in the repository root, and \texttt{copilot-instructions.md} in \path{.github/}.
For each file, the dataset stores the content and a SHA. We found that this SHA identifies the
file's content (a git blob), not a commit. To compare documents as they were at the same time, we
look for the \emph{snapshot commit}: the newest commit in the agent file's history at which the
file has exactly that content. We first search the commit history in the dataset and then, if
needed, the GitHub API. For our sample, \nSnapshotPackage{} snapshot commits came from the dataset
and \nSnapshotAPI{} from the API. They date from \snapshotFirst{} to \snapshotLast. At each
snapshot commit we find the README and CONTRIBUTING files the same way GitHub does: first in
\path{.github/}, then in the root, then in \path{docs/}. Every document we downloaded matches its
git SHA, so anyone can rebuild exactly the same set of documents.

\subsection{Filtering and sampling}

Table~\ref{tab:flow} shows how we filtered the files, step by step. We removed repositories that
no longer exist, forks (which copy another repository), archived repositories (which no longer
take contributions), and files whose snapshot commit we could not find. We also removed agent files
that are symbolic links or that only point to another file (for example, a \texttt{CLAUDE.md}
containing only \texttt{@AGENTS.md}), files not in English, and copies of another repository's
agent file (TF-IDF cosine similarity of 0.9 or more). The \nDuplicateDropped{} copies were mostly
rule packs installed by a tool, or mirrors of other projects~\cite{hata2021metamaintenance}.
Finally, we kept only repositories with both a README and a CONTRIBUTING file at the snapshot
commit. This last step removed \nDroppedNoContributing{} files, far more than any other step, and
left \nEligible{} files.

We sampled \nPerAgent{} files per agent type (random seed 507), so that we can compare the three
types fairly. We took at most one file per repository: \nMultiAgentRepos{} repositories in the
dataset have more than one agent file, and using each repository only once keeps the observations
independent. The \nSampleRepos{} repositories in our sample are larger than the average in the
dataset (median \sampleMedianStars{} stars). The three agent types are not equally common among
eligible files (\nEligibleCopilot{} Copilot, \nEligibleClaude{} \texttt{CLAUDE.md} and
\nEligibleAgents{} \texttt{AGENTS.md}). So when we report a result for all files together, we
weight each type by how common it is. We also marked two groups for robustness checks:
\nInitUnedited{} \texttt{CLAUDE.md} files that still have the header written by Claude Code's
\texttt{/init} command and were never edited, and \nStubContributing{} CONTRIBUTING files with
fewer than 50 words, which usually just point to a website.

\subsection{Splitting documents into sections}

A whole file is too large to show what is missing, and a single sentence is too small to hold a
rule together with its context. So we split every document at its headings into
\emph{sections}. We use second and third level headings, and first level headings when a
document uses several of them as section titles. Text before the first heading becomes its own
section, and documents without headings are split into blocks such as paragraphs and lists. We
parse the Markdown properly, so headings inside code blocks are ignored, and we drop tables of
contents. Table~\ref{tab:corpus} describes the result. There are \nUnits{} sections in total,
\nAgentUnits{} of them in agent files. The median agent file section has \agentUnitMedianWords{}
words, and the median repository has \agentUnitsPerRepoMedian{} agent file sections (the 90th
percentile is \agentUnitsPerRepoNinety, and the largest has \agentUnitsPerRepoMax).

If we labelled every agent file section, a few very long files would dominate the data. We
therefore labelled up to 10 randomly chosen sections per agent file, \nQueued{} sections in total.
\nFullyCodedRepos{} repositories have 10 sections or fewer and were labelled completely. When we
report shares over sections, we give each labelled section a weight that makes up for the
sections we did not label in its repository.

\subsection{Codebook}

Table~\ref{tab:codebook} summarises our codebook. For each agent file section we record four
things.

\begin{itemize}
\item[(A)] \textbf{Category:} which of the 16 instruction categories of Chatlatanagulchai et al.\
apply~\cite{chatlatanagulchai2026agentreadmes}. A section can have several.
\item[(C)] \textbf{Coverage:} whether the README and CONTRIBUTING from the same commit contain the
section's knowledge. A section is \emph{agent-only} if they do not, \emph{partially covered} if
they contain some of it, and \emph{shared} if they contain all of it. Sections that only talk to
the AI (for example, ``be concise'') are \emph{agent-directed} and are left out of the coverage
results. For partially covered and shared sections, we also mark which human sections cover them.
Two flags mark special cases: \emph{conflict}, when the human documents say something different,
and \emph{links out}, when they only point somewhere else, such as a website.
\item[(D1)] \textbf{Need:} for agent-only and partially covered sections, which we call
\emph{gap sections}, the newcomer need that the knowledge serves, taken from the landscape of
Dagenais et al.~\cite{dagenais2010landscape}.
\item[(D2)] \textbf{Barriers:} for gap sections, which newcomer barriers the knowledge would ease
if it were in the human documents. We use the barriers of Steinmacher et al.\ that documentation
can address~\cite{steinmacher2015barriers,santos2024onboarding}.
\end{itemize}

We judge knowledge, not wording. A paraphrase counts as coverage. A link to a website or wiki
does not. Mentioning the same topic without any of the section's details still counts as
agent-only. If a section mixes instructions for the agent with knowledge about the project, we
label it by its project knowledge.

\subsection{How we labelled and checked agreement}

We labelled the sections with a small tool built for this study. It shows the agent file section
next to the full README and CONTRIBUTING, with checkboxes to mark the human sections that cover
it. The tool never shows a similarity score or a ranking, so the labels are not influenced by the
matchers we test in RQ3. We split the work into three sets: a pilot set (\nPilotRepos{}
repositories, \nPilotUnits{} sections) to refine the codebook and tune the detector; a reliability
set (\nReliabilityRepos{} repositories, \nReliabilityUnits{} sections), chosen as whole
repositories with equal numbers per agent type; and the main set (\nMainRepos{} repositories,
\nMainUnits{} sections).

For the pilot and main sets, an LLM (Claude) first drafted each label from the codebook and the
three documents. The author then checked every draft against the documents in the tool. Of the
\nDraftsReviewed{} drafts, \nDraftsKept{} (\draftKeepRate) kept their coverage label and
\nDraftsCorrected{} were corrected. Corrections were most common for drafts that said
agent-directed (\draftCorrAgentDirected) or agent-only (\draftCorrAgentOnly, mostly changed to
partially covered), and least common for drafts that said shared (\draftCorrShared).
Table~\ref{tab:prov} shows how every label was made. The author labelled the
\nReliabilityUnits{} sections of the reliability set blind, without any draft.

\subsection{Analysis for RQ1 and RQ2}

\paragraph{Coverage.} We leave out agent-directed sections. Every remaining section is
agent-only, partially covered or shared. For each repository, we compute what share of its
sections falls into each of these three classes. For each agent type, we then average these
shares over its repositories. For all files together, we weight the three types by how common
they are among eligible files. This way every repository counts equally, however long its agent
file is, and the limit of 10 sections per repository does not affect the result. We get 95\%
confidence intervals by resampling repositories 1{,}000 times (a bootstrap~\cite{efron1993bootstrap}).

\paragraph{Categories and agent types.} Sections from the same repository are related to each
other, so ordinary tests over sections would make the results look more certain than they are. We
therefore fit a logistic regression that predicts whether a section is agent-only from its
categories and its agent type. We estimate it with generalised estimating equations (GEE), which
take into account that sections of the same repository are related~\cite{liang1986gee}. Each
category is compared with all sections that do not have it, while the other categories and the
agent type are held constant.

\paragraph{Needs and barriers.} For RQ2, we report how the needs and barriers of gap sections are
distributed. Each gap section has one need and can have several barriers.

\paragraph{Robustness.} We repeat the main estimate without the unedited \texttt{/init} files,
without the very short CONTRIBUTING files, and without sections whose topic the human documents
only link to. We also split the sample by how the labels were made: from a draft, or blind. Our
labels compare only with README and CONTRIBUTING, so we also estimate how much of the gap other
documents in the repository would close. For a subsample of repositories with Markdown files in
\path{docs/}, we run the RQ3 detector on the agent-only sections against README, CONTRIBUTING and
\path{docs/} together.

\subsection{The gap detector for RQ3}

\paragraph{Items.} An agent file section often holds several rules, and only some of them may be
covered. The detector therefore splits each section into \emph{items}: list entries, sentences
and code blocks. This gives \nItemsAgent{} agent items and \nItemsHuman{} human items, and it also
keeps each input short enough for embedding models.

\paragraph{Matchers.} We compare one matcher based on shared words with three embedding models.
The first is TF-IDF over single words and word pairs, with word weights computed from all
documents~\cite{salton1988termweighting}. The others are sentence embedding models of growing
size: all-MiniLM-L6-v2 with 23 million parameters~\cite{reimers2019sbert}, bge-base-en-v1.5 with
109 million~\cite{xiao2023cpack}, and Qwen3-Embedding-0.6B with 596 million~\cite{zhang2025qwen3embedding}.
Each matcher compares an agent file section only with the README and CONTRIBUTING of its own
repository, and produces three scores. \emph{Unit max} is the best similarity between the whole
section and any whole human section. \emph{Item mean} is the average, over the section's items, of
each item's best match. \emph{Item cov@$\tau$} is the share of items whose best match is above a
threshold $\tau$. The matcher also ranks the human sections, so a maintainer can see where a match
comes from. The matchers do not fully agree with each other (the rank correlation of their item
mean scores is between \matcherRhoMin{} and \matcherRhoMax), so the choice of matcher matters.
\ifllmjudge
An LLM judge~\cite{yang2025qwen3,zheng2023judge} then decides the borderline cases, using the five
best human sections that the matcher found.
\fi

\paragraph{Evaluation.} The main task is a yes or no question: is a section agent-only? The
\nPilotRepos{} pilot repositories (\detectorNDev{} sections) are used for tuning, and the other
repositories (\detectorNTest{} sections) for testing, so no repository is used for both. On the
pilot data only, we choose each matcher's score, the threshold that gives the best F1 for
agent-only, two more thresholds for predicting all three classes (agent-only, partial and shared),
and the matcher we release. On the test data, we report precision, recall and F1 for agent-only.
We also report the AUC, which measures how well the scores rank agent-only sections above covered
ones; the macro F1 over the three classes; and how often a human section that the annotator marked
as covering is ranked first (hit@1) or in the top five (hit@5). All results come with 95\%
confidence intervals from resampling repositories.

\section{Experimental Results}\label{sec:results}
%======================================================================

\subsection{The documents}

The three documents are about the same length (Table~\ref{tab:corpus}). The median agent file has
\agentWords{} words, the median README \readmeWords{} and the median CONTRIBUTING file
\contribWords. In the median repository, the agent file is \wordsGapContrib{} words longer than
CONTRIBUTING. Agent files are much harder to read than CONTRIBUTING files. Their median Flesch
Reading Ease score is \agentFlesch, against \contribFlesch{} for
CONTRIBUTING~\cite{flesch1948readability}; higher scores mean easier text. The agent file is the
harder one in \fleschHarderShare{} of \fleschPairs{} repositories (Wilcoxon signed rank test,
\fleschContribP). \texttt{CLAUDE.md} files are the hardest to read (\fleschClaude), followed by
Copilot instructions (\fleschCopilot) and \texttt{AGENTS.md} files (\fleschAgents). Agent files
tend to be dense lists of commands and rules, while CONTRIBUTING files tend to talk to the reader
in full sentences.

\subsection{RQ1: How much of the agent file is missing from the human documents?}

\paragraph{Most of what agent files say is not available to people.} On average,
\agentOnlyOverall{} of what a repository's agent file says is agent-only (Table~\ref{tab:rq1},
Figure~\ref{fig:rq1}a). Much of the rest is only partly covered, and only \sharedOverall{} is fully
shared with the README or CONTRIBUTING. So \anyGapOverall{} of what a project tells its agent is
missing, or only partly present, in the documents a new contributor reads. Very little of the
agent file is about the agent itself: only \agentDirectedOverall{} of sections speak only to the

\paragraph{The two documents sometimes disagree.} In \nConflictUnits{} sections, the human
documents contradict the agent file, for example by giving a different test command, package
manager or tool version. One of the two must then be out of date, and a newcomer who follows
CONTRIBUTING may fail where the agent succeeds. In \nLinksOutUnits{} sections, the human documents
point to a website or wiki for the topic. Our coverage label does not count such links.

\subsection{RQ2: Which newcomer needs and barriers does the gap relate to?}

\paragraph{Needs.} \needGroupTopShare{} of gap sections serve \emph{\needGroupTop} needs
(Table~\ref{tab:rq2needs}). The largest needs are \emph{\needTopOne} (\needTopOneShare), which
covers how changes are made, checked and submitted, and \emph{\needTopTwo} (\needTopTwoShare), which
covers how to set up, build, run and debug the project. Knowledge about the product makes up
\needGroupProduct, mostly \emph{\needTopThree} (\needTopThreeShare) and detailed design and runtime
behaviour. Documentation needs, such as where to find things, make up \needGroupDocs. Needs about
the team and the wider context hardly appear (\needGroupTeamContext). Agent files do not say whom
to ask or how the community works, because an agent does not need that.

\paragraph{Barriers.} If the missing knowledge were in the human documents, it would most often
help with three barriers: \emph{\barrierTopOne} (\barrierTopOneShare{} of gap sections),
\emph{\barrierTopTwo} (\barrierTopTwoShare) and \emph{\barrierTopThree} (\barrierTopThreeShare;
Table~\ref{tab:rq2bar}). Newcomers report these barriers often~\cite{steinmacher2015barriers}.
Barriers about finding one's way, such as finding a task or knowing how contributions are
accepted, rarely appear. Agent files are about doing the work, not about finding it or getting it
merged. This makes our gap different from the one Fronchetti et al.\ found in CONTRIBUTING files,
which most often leave out how to choose a task and how to talk to the
community~\cite{fronchetti2023contributing}. Agent files do not cover those barriers either. But
they do cover the process and technical barriers, only for the agent.

and practical: commands to run, the folder that holds a component, pitfalls of the runtime, the
steps of a recurring task. Without them, a newcomer would have to ask a maintainer or dig through
the code to learn these things.

\subsection{RQ3: Can we find the missing knowledge automatically?}

\paragraph{A simple matcher finds most gaps.} On the \detectorNTest{} test sections, all four
matchers perform about the same (F1 for agent-only between \detectorFOneMin{} and
\detectorFOneMax, AUC between \detectorAUCMin{} and \detectorAUCMax; Table~\ref{tab:rq3}). The
matcher chosen on the pilot data, \detectorBestMatcher{} with the \emph{\detectorBestVariant}
score (F1 \detectorDevFOne{} on the pilot data), finds agent-only sections with recall
\detectorRecall{} and precision \detectorPrecision{} (F1 \detectorFOne). For \detectorHitFive{} of
the covered sections, a human section that covers it is among its top five suggestions, and for
\detectorHitOne{} it is the first one. Larger embedding models do not help. A likely reason is
that an agent file and the human documents of the same project use the same words: command names,
file paths and tool names. Matching on shared words handles these well.

\paragraph{Telling partial from shared coverage is harder.} The macro F1 over the three classes is
only \detectorMacroFOne. Whether a section is fully shared depends on whether every one of its
rules is present, and a similarity score captures this only roughly.

\paragraph{Errors.}
\ifdefined\detectorFalseAgentOnly
Most errors are covered sections that the detector flags as agent-only (\detectorFalseAgentOnly)
rather than agent-only sections that it misses (\detectorMissedAgentOnly). The false alarms are
typically partially covered sections whose topic appears in the human documents in different
words, such as an architecture summary written another way, or a build command explained in
prose. With the ranked suggestions, a maintainer can dismiss these quickly. The missed agent-only
sections often share many words with the human documents, but not the rule itself. Examples are
lists of commands for the same tool (\texttt{mise run lint}, \texttt{bun test}) whose specific
subcommands never appear in the human documents.
\fi
For the intended use, which is pointing maintainers to sections worth adding to CONTRIBUTING, high
recall with ranked suggestions matters more than precision.

\section{Discussion}\label{sec:discussion}
%======================================================================

\paragraph{Projects onboard their agents better than their people.} The knowledge that newcomers
find hardest to get, such as the development process, the environment, and the structure and
pitfalls of the code, is written down in most of the repositories we studied. It is just written
in the file meant for the agent. We see three possible reasons. First, an agent cannot ask a
maintainer, so everything it needs must be written down. A human newcomer is expected to read the
code, ask on the issue tracker or learn by doing. Second, writing for an agent pays off right
away. An instruction that prevents a wrong command helps in the very next session, while the
benefit of better human documentation is slow and hard to see. Third, tools such as Claude Code's
\texttt{/init} write a first agent file from the code, and nothing like that exists for
CONTRIBUTING files.

\paragraph{Agent files are a ready source for contributor documentation.} For maintainers, this
means that much of the work of improving onboarding documents is already done. Agent-only sections
about building, testing, the environment and the architecture can be moved or adapted into
CONTRIBUTING, and a simple detector is enough to find them. With recall \detectorRecall{} and
ranked suggestions, \texttt{gapcheck} turns the comparison into a short review. Copying alone is
not enough, though. Agent files are terser and harder to read than CONTRIBUTING files (Flesch
\agentFlesch{} against \contribFlesch), and instructions about the agent's own tools and behaviour
make no sense to a person. Maintainers can also avoid the duplication altogether. They can keep
shared knowledge in one document written for people, and point the agent file to it. Some projects
already do this, which is why we left out agent files that only link elsewhere.

\paragraph{The two documents drift apart.} The \nConflictUnits{} contradictions we found show that
two parallel documents are hard to keep in sync. Running a detector in continuous integration
could flag new agent-only knowledge and possible contradictions whenever either file changes, much
like existing work on finding documentation issues~\cite{aghajani2019issues}.

\paragraph{What tool builders can do.} The companies behind coding agents shape what maintainers
write. They choose the file names, generate first drafts and recommend what to include. Their
tools could also suggest matching updates to CONTRIBUTING, or read the human documents first and
generate only what is specific to the agent. A shared format such as \texttt{AGENTS.md} would make
this easier.

\paragraph{What researchers can do.} Agent files write down project knowledge that onboarding
research has so far had to collect through interviews and
observation~\cite{dagenais2010landscape,steinmacher2015social}. They show what maintainers think
is needed to work on their project, and our results suggest that this is mostly about process and
environment. Future work could test whether moving agent-only knowledge into CONTRIBUTING actually
helps human newcomers, for example by measuring how many first contributions succeed. It could
also track whether the gap grows or shrinks as the files change over time.

\section{Limitations and Threats to Validity}\label{sec:limitations}
%======================================================================

\paragraph{Construct validity.} We compare agent files only with the README and CONTRIBUTING.
Projects also document themselves in wikis, on websites and in \path{docs/} folders, and knowledge
found only there counts as agent-only in our study. Our \path{docs/} check gives an idea of how
much the documents inside the repository would change this, and our \emph{links out} check covers
pointers to other places, but neither covers websites. Coverage is a judgement about knowledge,
not text. The codebook's rules and examples make it repeatable, but the line between partial and
shared coverage is the main source of disagreement (Table~\ref{tab:rel}). Finally, we labelled
newcomer needs and barriers from the text, not from real newcomers. They describe which needs the
knowledge would serve, not which needs newcomers actually had.

\paragraph{Internal validity.} \nDraftsReviewed{} of the \nCodedUnits{} labels started from an LLM
draft that the author reviewed, and the author kept the drafted coverage in \draftKeepRate{} of
cases. The final labels may therefore carry over the drafting model's judgement. The
\nDraftsCorrected{} corrections show that the drafts were sometimes wrong, but they cannot tell us
how many wrong drafts were missed. The reliability set, labelled without drafts, has a lower
agent-only share than the drafted sets (\agentOnlyBlind{} against \agentOnlyDrafted;
Table~\ref{tab:sens}). Part of this difference may come from the drafts and part from the
different repositories. Our main estimate should therefore be read together with the blind
estimate.
\ifsecondcoder\ifsecondcoderllm
We measured agreement on that set with an LLM annotator, which may share blind spots with the
drafting model. We did not measure agreement between two people, and this remains the most
important open check. \nNeedFromSecond{} need labels also come from this annotator.
\fi\else
The coverage labels come from one annotator, and agreement with a second one is still pending.
\fi
The snapshot commit keeps the three documents consistent with each other, but whether a
repository is a fork or archived is based on its status today, not at the time of the snapshot.

\paragraph{External validity.} Requiring a CONTRIBUTING file removes most repositories and leaves
larger, more established projects (median \sampleMedianStars{} stars). Smaller projects, most of
which have no CONTRIBUTING file, may have an even bigger gap. We studied three file types, in
English, from one dataset collected between \snapshotFirst{} and \snapshotLast. These files change
quickly, and other agents, such as Cursor with its rule files, may differ. Mining GitHub has known
pitfalls~\cite{kalliamvakou2014perils}. We reduced them by removing forks, archived repositories,
copies, and files that only link elsewhere.

\paragraph{Conclusion validity.} Sections are grouped within repositories. We therefore estimate at
the repository level, resample whole repositories, and use models that account for the grouping.
With \geeNTerms{} terms in the regression, some significant odds ratios could appear by chance.
After a Bonferroni correction, \geeBonferroniCats{} are still significant. The detector's
thresholds were tuned on only \detectorNDev{} sections, and the confidence intervals on the test
data show the uncertainty that this leaves.

%======================================================================
\section{Conclusion}\label{sec:conclusion}
%======================================================================

Projects tell their coding agents a lot that they do not tell their contributors. In
\nSampleRepos{} repositories that have all three documents, \agentOnlyOverall{} of what the agent
file says is missing from the README and CONTRIBUTING of the same commit (\agentOnlyBlind{} in the
repositories labelled blind), and \anyGapOverall{} is not fully available to people. The gap shows
up in most repositories and for all three types of agent file. It is about how to work on the
project: the development process, the environment, the architecture and its pitfalls. That is the
very knowledge whose absence makes newcomers give up. Because this knowledge already exists in the
repository, a simple text matcher can point maintainers to most of it. We hope that maintainers
will use their agent files to improve their contributor documentation, and that agent tools will
help them keep both kinds of newcomer equally well informed.
