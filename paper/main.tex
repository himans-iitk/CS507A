\title{What We Tell the Agent but Not the Newcomer}
\subtitle{Mining Agent Context Files for Gaps in Human Onboarding Documentation}

\author{Himanshu Mishra}

\begin{abstract}
AI coding agents such as Claude Code, OpenAI Codex and GitHub Copilot read a repository context
file at the start of every session. This file tells the agent how to build, test and change the
project, which is the same knowledge a new human contributor needs. Human newcomers,
however, rely on the README and CONTRIBUTING files, and no study has examined whether the knowledge
written for agents also reaches them. This paper aims to find the onboarding knowledge that projects
give only to their agents, to show which newcomer needs it would serve, and to detect it
automatically so that maintainers can move it into their contributor documentation. We sampled \nSampleRepos{} GitHub repositories with an agent file, a README and a
CONTRIBUTING file, and compared the three documents at the same commit. We manually labelled
\nQueued{} agent file sections for their coverage in the human documents, their instruction
category, and the newcomer needs and barriers they address. On average, \agentOnlyOverall{} of a
repository's agent file knowledge is absent from its human documentation, and only
\sharedOverall{} is fully shared. The missing knowledge concerns how to work on the project:
\needGroupTopShare{} of it serves process and practice needs, mainly the development workflow and
environment. A lexical matcher based on term frequency and inverse document
frequency (TF-IDF) detects this knowledge with an F1 score of \detectorFOne{} on unseen
repositories. Agent files are therefore a ready
source of material for improving contributor documentation. We release the data, codebook, labels,
pipeline and detector.
\end{abstract}

\section{Introduction}
%======================================================================

Starting on a new software project is a difficult task. Before making a first change, a newcomer has to work
out how the code is organised, how to set up a working environment, which commands build and test
the project, and which unwritten rules every change must
follow~\cite{sim1998rampup,begel2008novice,dagenais2010landscape}. In open source,
mentors are rarely available, and many newcomers give up before their first contribution. The
barriers they report most often include missing knowledge of the project's process, problems with
the local environment, and difficulty finding their way in the
code~\cite{steinmacher2015barriers,steinmacher2015social}. Projects address these barriers with a
README that explains what the project is and a CONTRIBUTING file that explains how to work on
it~\cite{prana2019readme,steinmacher2019letmein}.

Since 2025, projects also write documentation for a second kind of newcomer. AI coding agents such
as Claude Code, OpenAI Codex and GitHub Copilot load a \emph{context file} into every session:
\texttt{CLAUDE.md}, \texttt{AGENTS.md} or
\path{.github/copilot-instructions.md}~\cite{chatlatanagulchai2026agentreadmes,mohsenimofidi2026context}.
An agent starts in the same position as a human newcomer: it knows the programming language but
not the project. Maintainers therefore tell it how to build and test, how the code is organised,
which conventions to follow and which files not to touch. Such files help agents most when they
contain this kind of practical project knowledge~\cite{gloaguen2026agentsmd}.

\paragraph{Motivation.} Four observations motivate this study.
\begin{enumerate}
\item \emph{Human onboarding documents are incomplete.} In a study of CONTRIBUTING files, 52\% of
projects omitted at least three of six common newcomer barriers~\cite{fronchetti2023contributing}.
\item \emph{Agent files are already widespread.} The Agent READMEs dataset alone contains
\nPackageFiles{} agent files from \nPackageRepos{} GitHub
repositories~\cite{chatlatanagulchai2026agentreadmes}, and \nMultiAgentRepos{} of these
repositories maintain more than one.
\item \emph{Many projects write for their agent but not for their contributors.} Of the
\nWithReadme{} agent files that pass our screening and whose repository has a README, only
\withContributingShare{} come with a CONTRIBUTING file. In the other \withoutContributingShare{},
the agent file is the only document written specifically for someone who will change the code.
\item \emph{Where both exist, maintainers write more for the agent.} In our sample, the agent file
is longer than CONTRIBUTING in \agentLongerShare{} of repositories (median \agentWords{} against
\contribWords{} words).
\end{enumerate}
Figure~\ref{fig:overview} shows a typical case from our data. The \texttt{AGENTS.md} of
\texttt{microsoft/generative-ai-with-javascript} tells the agent to install Node.js 20 or later,
set a \texttt{GITHUB\_TOKEN} variable, and run \texttt{npm install} and \texttt{npm start}. Neither
the README nor the CONTRIBUTING file of the same commit gives these setup steps, so a human newcomer
must discover them alone. If such cases are common, projects onboard their agents better than
their people, and the agent file is a ready source for improving the human documents.

\input{figures/overview}

Prior studies examined agent files in
isolation~\cite{chatlatanagulchai2026agentreadmes,mohsenimofidi2026context} and onboarding
documents in isolation~\cite{prana2019readme,fronchetti2023contributing}. To the best of our
knowledge, no study has measured how much of the agent's knowledge reaches people within the same
repository. This paper addresses three
research questions (RQs):

\begin{itemize}
\item \textbf{RQ1:} How much of the knowledge in agent context files is absent from the README and
CONTRIBUTING of the same repository?
\item \textbf{RQ2:} Which newcomer needs and onboarding barriers does this agent-only knowledge
address?
\item \textbf{RQ3:} How accurately can agent-only knowledge be detected automatically?
\end{itemize}

To answer them, we start from the Agent READMEs dataset~\cite{chatlatanagulchai2026agentreadmes}
and take each agent file together with the README and CONTRIBUTING of the same commit. We sample
\nSampleRepos{} repositories, \nPerAgent{} per agent file type, and split all documents at their
headings into \nUnits{} sections. We then manually label \nQueued{} agent file sections with a
codebook that combines an existing taxonomy of agent instructions~\cite{chatlatanagulchai2026agentreadmes},
a coverage scale, the newcomer landscape of Dagenais et al.~\cite{dagenais2010landscape} and the
onboarding barriers of Steinmacher et al.~\cite{steinmacher2015barriers}. Finally, we evaluate
lexical and embedding matchers that predict the coverage label from the documents alone.

\begin{tcolorbox}[colback=black!3,colframe=black!35,boxrule=0.4pt,arc=1pt,left=4pt,right=4pt,top=3pt,bottom=3pt]
\small\textbf{Key findings.}
\begin{itemize}\setlength{\itemsep}{1pt}\setlength{\topsep}{2pt}\setlength{\leftmargin}{1em}
\item \textbf{RQ1:} On average, \agentOnlyOverall{} of a repository's agent file knowledge is
absent from its README and CONTRIBUTING, and \anyGapOverall{} is absent or only partly present.
\repoAnyAgentOnlyShare{} of repositories have some agent-only knowledge. \catHighOne,
\catHighTwo{} and \catHighThree{} instructions are most often agent-only; \catLow{} instructions
least often (\catLowShare).
\item \textbf{RQ2:} \needGroupTopShare{} of the missing knowledge serves \emph{\needGroupTop}
needs. It would most often ease the barrier \emph{\barrierTopOne}.
\item \textbf{RQ3:} TF-IDF detects agent-only sections with F1 \detectorFOne{} (recall
\detectorRecall), compared with \baselineFOne{} for a trivial baseline. Sentence embeddings perform
no better.
\end{itemize}
\end{tcolorbox}

\noindent This paper makes the following contributions:
\begin{itemize}
\item The first comparison of agent context files with human onboarding documentation within the
same repository, at section level, with population estimates for three agent file types.
\item A characterisation of the missing knowledge in terms of established models of newcomer needs
and onboarding barriers.
\item \texttt{gapcheck}, a gap detector, evaluated on repositories not used for tuning.
\item A replication package with the documents, the codebook, \nCodedUnits{} labels and their
provenance, and a pipeline that regenerates every number, table and figure in this paper with a
single command.
\end{itemize}

The rest of this paper is organised as follows. Section~\ref{sec:related} reviews related work.
Section~\ref{sec:method} describes the methodology and Section~\ref{sec:results} the results.
Section~\ref{sec:discussion} discusses their implications, Section~\ref{sec:limitations} the limitations and
threats to validity, and Section~\ref{sec:conclusion} concludes.

\section{Related Work}\label{sec:related}
%======================================================================

\subsection{Coding agents and context files}

Large language models (LLMs) now support most software engineering activities~\cite{hou2024llm4se}.
Coding agents go beyond code completion: they explore a repository, run commands and submit
changes on their own. Benchmarks such as SWE-bench measure how well they resolve real GitHub
issues~\cite{jimenez2024swebench}, and the design of an agent's tools strongly affects its
success~\cite{yang2024sweagent}. Developers report that AI assistants often miss their
requirements and are hard to steer~\cite{liang2024usability}. Context files respond to this
problem. They are Markdown files, loaded into every session, in which maintainers describe the
project for the agent.

Three studies have examined these files. Chatlatanagulchai et al.\ collected \nPackageFiles{}
files from GitHub, grouped their instructions into 16 categories, and found them hard to
read~\cite{chatlatanagulchai2026agentreadmes}. Mohsenimofidi et al.\ studied how open source
projects engineer the context they give AI agents~\cite{mohsenimofidi2026context}. Gloaguen et
al.\ found that \texttt{AGENTS.md} files help agents most when they describe practices specific to
the project~\cite{gloaguen2026agentsmd}. All three treat the agent file in isolation. Unlike them,
this study relates the agent file to the documentation that the same project writes for people.
We reuse the dataset and the 16 categories of Chatlatanagulchai et al.

\subsection{Newcomer onboarding}

Onboarding has long been recognised as a problem. Sim and Holt described how new developers, whom
they called ``software immigrants'', settle into a project~\cite{sim1998rampup}. Begel and Simon
observed new hires who had to learn their team's tools and processes before they could
contribute~\cite{begel2008novice}, and Ko et al.\ catalogued the information needs of developers
in teams~\cite{ko2007information}. Dagenais et al.\ described the \emph{landscape} that newcomers
must learn~\cite{dagenais2010landscape}. It covers the product (architecture, design,
technologies, domain), processes and practices (development and task processes, environment and
tools, configuration management), the team, the documentation, and the wider context.

For open source, Steinmacher et al.\ consolidated the barriers that newcomers face, including
orientation problems, gaps in the newcomers' own knowledge, documentation problems and technical
hurdles~\cite{steinmacher2015barriers,steinmacher2015social}. They also built a portal that lowered
these barriers~\cite{steinmacher2016portal} and derived guidelines for
maintainers~\cite{steinmacher2019letmein}. Santos et al.\ review the onboarding tools proposed
since~\cite{santos2024onboarding}, and Tan et al.\ studied ``good first issues'' as a way to help
newcomers choose a task~\cite{tan2020goodfirst}. Closest to our work, Fronchetti et al.\ checked
CONTRIBUTING files against the barrier model and found that most projects leave several barriers
unaddressed~\cite{fronchetti2023contributing}. While they asked which barriers human
documentation omits, we ask which barriers a project already addresses in writing, but only for
its agent. We use the landscape of Dagenais et al.\ and the barriers of Steinmacher et al.\ to
classify this knowledge.

\subsection{Developer documentation}

Developers rely on documentation but often find it incomplete or
outdated~\cite{lethbridge2003documentation,aghajani2019issues,aghajani2020practitioners}, and poor
documentation is a main obstacle to learning an API~\cite{robillard2009apis}. Prana et al.\
classified the content of GitHub READMEs and found that they mostly describe what a project is and
how to use it, and less often how to contribute~\cite{prana2019readme}. Elazhary et al.\ showed that
the actual contribution process of many projects diverges from their CONTRIBUTING
guidelines~\cite{elazhary2019guidelines}. Documentation can also be improved from external sources,
for example by adding insights from Stack Overflow to API documentation~\cite{treude2016augmenting}.
In contrast to such external sources, the agent file is written by the project's own maintainers
and already sits in the repository.

\subsection{Document matching and LLM-assisted labelling}

Deciding whether one text covers another is a long-standing information retrieval task in software
engineering. Traceability recovery links documentation to code with TF-IDF and vector space
models~\cite{antoniol2002traceability,salton1988termweighting} or latent semantic
indexing~\cite{marcus2003lsi}, and sentence embeddings are now the common choice for semantic
similarity~\cite{reimers2019sbert}. We compare both families on a new task: matching agent
instructions to sections of human documentation.

LLMs are increasingly used to label text. They match or exceed crowd workers on some annotation
tasks~\cite{gilardi2023chatgpt}. In software engineering, they can replace part but not all of the
human effort, and agreement between models indicates which tasks are
suitable~\cite{ahmed2025llmannotation}. LLMs also serve as judges of other models'
output~\cite{zheng2023judge}. This study uses an LLM in two roles, to draft labels that a person
reviews and as an independent second annotator, and reports the effect of both on validity.

\section{Methodology}\label{sec:method}
%======================================================================

Figure~\ref{fig:overview} shows the architecture of the method. The top row lists the six
stages; the bottom row traces one real section from our data through every stage, which serves as
a running example in this section. A single pipeline implements every stage, and its outputs feed
this paper directly.



\subsection{Data source and snapshot commit}

The study builds on the Agent READMEs dataset~\cite{chatlatanagulchai2026agentreadmes}. It contains
\nPackageFiles{} agent files from \nPackageRepos{} GitHub repositories: \texttt{CLAUDE.md} and
\texttt{AGENTS.md} in the repository root, and \texttt{copilot-instructions.md} in \path{.github/}.
For each file, the dataset stores the content and a git hash. We found that this hash identifies
the file content (a git blob) rather than a commit. To compare documents as they stood together,
we recover the \emph{snapshot commit}: the newest commit in the agent file's history at which the
file has exactly that content. We search the dataset's commit history first and the GitHub API as
a fallback; \nSnapshotPackage{} sampled snapshots come from the dataset and \nSnapshotAPI{} from
the API, dated \snapshotFirst{} to \snapshotLast. At each snapshot commit, we locate the README and
CONTRIBUTING the way GitHub does: in \path{.github/}, then the root, then \path{docs/}. Every
downloaded document matches its git hash, so the corpus can be rebuilt exactly.

\subsection{Filtering and sampling}

Table~\ref{tab:flow} lists the filtering steps, applied in a fixed order. We removed repositories
that no longer exist, forks (which duplicate another repository), archived repositories (which no
longer accept contributions), and files whose snapshot commit could not be found. We also removed
agent files that are symbolic links or only point to another file (for example, a
\texttt{CLAUDE.md} containing only \texttt{@AGENTS.md}), files not in English, and copies of
another repository's agent file (TF-IDF cosine similarity of at least 0.9). The
\nDuplicateDropped{} copies were mostly tool-installed rule packs and mirrored
projects~\cite{hata2021metamaintenance}. Finally, we required a README and a CONTRIBUTING file at
the snapshot commit. This step removed \nDroppedNoContributing{} files, more than all other steps
together, and left \nEligible{} eligible files.

\input{tables/flow}

We sampled \nPerAgent{} files per agent type (random seed 507), so that the three types can be
compared with equal precision. We drew at most one file per repository, because
\nMultiAgentRepos{} repositories in the dataset have more than one agent file and repeated
repositories would not be independent. The sampled repositories are larger than the dataset
average (median \sampleMedianStars{} stars). Because the three types are not equally common among
eligible files (\nEligibleCopilot{} Copilot, \nEligibleClaude{} \texttt{CLAUDE.md},
\nEligibleAgents{} \texttt{AGENTS.md}), overall estimates weight each type by its share of the
eligible population. Two subsets were flagged for robustness checks: \nInitUnedited{}
\texttt{CLAUDE.md} files that still carry the header of Claude Code's \texttt{/init} command and
were never edited, and \nStubContributing{} CONTRIBUTING files with fewer than 50 words, which
usually point to a website.

\subsection{Unit of analysis: sections}

A whole file is too coarse to show what is missing, and a single sentence is too fine to hold a
rule together with its context. We therefore split every document at its headings into
\emph{sections}: second and third level headings, and first level headings where a document uses
several of them as section titles. Text before the first heading forms its own section, and
documents without headings are split into top level blocks. Headings inside code blocks are
ignored, and tables of contents are removed. Table~\ref{tab:corpus} summarises the result:
\nUnits{} sections, of which \nAgentUnits{} are in agent files. The median agent file section has
\agentUnitMedianWords{} words, and the median repository has \agentUnitsPerRepoMedian{} agent file
sections (90th percentile \agentUnitsPerRepoNinety, maximum \agentUnitsPerRepoMax).

\input{tables/corpus}

Labelling every agent file section would let a few long files dominate the data. We therefore
labelled up to 10 randomly chosen sections per agent file, \nQueued{} sections in total;
\nFullyCodedRepos{} repositories were labelled completely. Where results are reported over
sections, each section is weighted to represent the unlabelled sections of its repository.

\subsection{Codebook}

Table~\ref{tab:codebook} summarises the codebook. Each agent file section receives four labels:

\begin{itemize}
\item[(A)] \textbf{Category:} all of the 16 instruction categories of Chatlatanagulchai et al.\
that apply~\cite{chatlatanagulchai2026agentreadmes}.
\item[(C)] \textbf{Coverage:} whether the README and CONTRIBUTING of the same commit contain the
section's knowledge. A section is \emph{agent-only} if they do not, \emph{partially covered} if
they contain part of it, and \emph{shared} if they contain all of it. Sections that only address
the AI (for example, ``be concise'') are \emph{agent-directed} and are excluded from the coverage
results. Two flags mark special cases: \emph{conflict}, when the human documents contradict the
section, and \emph{links out}, when they only point elsewhere.
\item[(D1)] \textbf{Need:} for agent-only and partially covered sections, together called
\emph{gap sections}, the newcomer need served, from the landscape of Dagenais et
al.~\cite{dagenais2010landscape}.
\item[(D2)] \textbf{Barriers:} for gap sections, the barriers of Steinmacher et al.\ that the
knowledge would ease if it were in the human
documents~\cite{steinmacher2015barriers,santos2024onboarding}.
\end{itemize}

Coverage judges knowledge rather than wording. A paraphrase counts as coverage; a link to a
website or wiki does not; mentioning the same topic without the section's specific details is
still agent-only. A section that mixes agent-directed sentences with project knowledge is labelled
by its project knowledge. In the running example (Figure~\ref{fig:overview}), the README and
CONTRIBUTING mention neither Node.js nor \texttt{GITHUB\_TOKEN}, so the section is agent-only; it
serves the need \emph{Development Environment and Tools} and would ease the barrier \emph{Local
environment setup hurdles}.

\subsection{Labelling procedure and reliability}

Labelling used a purpose-built tool that shows the agent file section next to the full README and
CONTRIBUTING, with checkboxes for the covering human sections. The tool never shows a similarity
score or ranking, so the labels are independent of the matchers evaluated in RQ3. The work was
divided into a pilot set (\nPilotRepos{} repositories, \nPilotUnits{} sections) for refining the
codebook and tuning the detector; a reliability set (\nReliabilityRepos{} repositories,
\nReliabilityUnits{} sections), drawn as whole repositories with equal numbers per agent type; and
the main set (\nMainRepos{} repositories, \nMainUnits{} sections).

For the pilot and main sets, an LLM (Claude) drafted each label from the codebook and the three
documents, and the author reviewed every draft against the documents in the tool. Of the
\nDraftsReviewed{} drafts, \nDraftsKept{} (\draftKeepRate) kept their coverage label and
\nDraftsCorrected{} were corrected. Corrections were most frequent for drafts labelled
agent-directed (\draftCorrAgentDirected) or agent-only (\draftCorrAgentOnly, mostly changed to
partially covered), and least frequent for drafts labelled shared (\draftCorrShared).
Table~\ref{tab:prov} gives the origin of every label. The author labelled the
\nReliabilityUnits{} sections of the reliability set blind, without drafts.

\subsection{Analysis for RQ1 and RQ2}

\paragraph{Coverage estimates.} Agent-directed sections are excluded, so every remaining section is
agent-only, partially covered or shared. For each repository, we compute the share of its sections
in each class and average these shares over the repositories of each agent type. The overall
estimate weights the three types by their share of eligible files. Every repository therefore
counts equally, regardless of the length of its agent file, and the limit of 10 sections per
repository does not bias the result. We assess uncertainty with 1{,}000
bootstrap samples that resample repositories within each agent type~\cite{efron1993bootstrap}; the
resulting confidence intervals are reported in the replication package.

\paragraph{Categories and agent types.} Sections of the same repository are correlated, so tests
that treat sections as independent would overstate significance. We therefore fit a logistic
regression for agent-only with indicators for each category and the agent type, estimated with
generalised estimating equations (GEE) clustered by repository~\cite{liang1986gee}. Each category is
compared with all sections that lack it, holding the other categories and the agent type constant.

\paragraph{Needs and barriers.} For RQ2, we report the weighted distribution of needs (one per gap
section) and barriers (any number per gap section).

\paragraph{Robustness.} We recompute the main estimate without unedited \texttt{/init} files,
without short CONTRIBUTING files, and without sections whose topic the human documents only link
to. We also compare repositories labelled from drafts with those labelled blind. Because labels
compare against README and CONTRIBUTING only, we further estimate how much of the gap other
documents in the repository would close: for a subsample of repositories with Markdown files in
\path{docs/}, the RQ3 detector compares agent-only sections against README, CONTRIBUTING and
\path{docs/} together.

\subsection{Gap detector for RQ3}

\paragraph{Items.} An agent file section often contains several rules, of which only some may be
covered. The detector therefore splits each section into \emph{items} (list entries, sentences
and code blocks), giving \nItemsAgent{} agent items and \nItemsHuman{} human items. Short items also
fit within the input limits of embedding models.

\paragraph{Matchers.} We compare one lexical matcher with three embedding models. The lexical
matcher uses TF-IDF over words and word pairs, with weights computed on all
documents~\cite{salton1988termweighting}. The embedding models increase in size: all-MiniLM-L6-v2
(23 million parameters)~\cite{reimers2019sbert}, bge-base-en-v1.5 (109
million)~\cite{xiao2023cpack} and Qwen3-Embedding-0.6B (596 million)~\cite{zhang2025qwen3embedding}.
Each matcher compares an agent file section only with the README and CONTRIBUTING of its own
repository and computes three scores: \emph{unit max}, the best similarity between the whole
section and any whole human section; \emph{item mean}, the mean over items of each item's best
match; and \emph{item cov@$\tau$}, the share of items whose best match exceeds a threshold $\tau$.
The matcher also ranks the human sections, which shows a maintainer where a match comes from. Figure~\ref{fig:overview} shows these scores for the running example: none
of its four items has a close match in the human documents, so its item mean falls below the
threshold and the section is predicted agent-only. The
matchers agree only partly (rank correlation of item mean between \matcherRhoMin{} and
\matcherRhoMax), so the choice of matcher matters.
\ifllmjudge
An LLM judge~\cite{yang2025qwen3,zheng2023judge} then decides borderline cases from the matcher's
five best candidate sections.
\fi

\paragraph{Evaluation protocol.} The primary task is binary: is a section agent-only? The
\nPilotRepos{} pilot repositories (\detectorNDev{} sections) form the development set and the
remaining repositories (\detectorNTest{} sections) the test set, so no repository appears in both.
On the development set only, we select each matcher's score, the threshold that maximises F1 for
agent-only, two further thresholds for a three class prediction (agent-only, partial, shared), and
the matcher to release. On the test set, we report precision, recall and F1 for agent-only; the
area under the ROC curve (AUC); macro F1 over the three classes; and how often a human section
marked as covering is ranked first (hit@1) or among the top five (hit@5). As a baseline, we label
every section agent-only.

\subsection{Implementation}

The pipeline is written in Python. It parses Markdown with markdown-it-py, fits the regression
with statsmodels, computes readability with textstat, and computes embeddings with
sentence-transformers on a single GPU. All responses from the GitHub API are cached, and every
step is deterministic given the cache and the random seed. One command reruns all stages from the
frozen labels and rebuilds this paper.

\subsection{Corpus characteristics}

Table~\ref{tab:corpus} shows that the three documents are of similar length. The median agent
file has \agentWords{} words, the median README \readmeWords{} and the median CONTRIBUTING file
\contribWords; within a repository, the agent file is a median of \wordsGapContrib{} words longer
than CONTRIBUTING. Agent files are considerably harder to read than CONTRIBUTING files, with a
median Flesch Reading Ease of \agentFlesch{} against \contribFlesch{}~\cite{flesch1948readability}
(higher is easier). The agent file is the harder one in \fleschHarderShare{} of \fleschPairs{}
repositories (Wilcoxon signed rank test, \fleschContribP). \texttt{CLAUDE.md} files are the
hardest (\fleschClaude), followed by Copilot instructions (\fleschCopilot) and \texttt{AGENTS.md}
(\fleschAgents). Agent files tend to be dense lists of commands and rules, whereas CONTRIBUTING
files address the reader in prose.

\paragraph{The two documents sometimes contradict each other.} In \nConflictUnits{} sections, the

\subsection{RQ2: Newcomer needs and barriers}

\paragraph{Needs.} Table~\ref{tab:rq2needs} shows that \needGroupTopShare{} of gap sections serve
\emph{\needGroupTop} needs. The largest are \emph{\needTopOne} (\needTopOneShare), which covers

behaviour. Documentation needs, such as where to find information, account for \needGroupDocs.
Team and context needs are nearly absent (\needGroupTeamContext): agent files do not explain whom
to ask or how the community works, because an agent does not need this.

\paragraph{Barriers.} If the missing knowledge were in the human documents, it would most often
ease \emph{\barrierTopOne} (\barrierTopOneShare{} of gap sections), \emph{\barrierTopTwo}
(\barrierTopTwoShare) and \emph{\barrierTopThree} (\barrierTopThreeShare; Table~\ref{tab:rq2bar}).
Newcomers report these barriers frequently~\cite{steinmacher2015barriers}. Orientation barriers,
such as finding a task or understanding how contributions are accepted, rarely appear, because
agent files concern doing the work rather than finding it or getting it merged. The gap therefore
differs from the one Fronchetti et al.\ found in CONTRIBUTING files, which most often omit how to
choose a task and how to communicate with the community~\cite{fronchetti2023contributing}. Agent
files do not address those barriers either, but they do address the process and technical
barriers, for the agent only.

obtain this knowledge.

\subsection{RQ3: Automatic detection}

\paragraph{A lexical matcher detects most agent-only knowledge.} Table~\ref{tab:rq3} shows that
all four matchers perform similarly on the \detectorNTest{} test sections (F1 for agent-only
between \detectorFOneMin{} and \detectorFOneMax, AUC between \detectorAUCMin{} and

precision \baselinePrecision. The matcher selected on the development set, \detectorBestMatcher{}
with the \emph{\detectorBestVariant} score (development F1 \detectorDevFOne), achieves recall
\detectorRecall{} at precision \detectorPrecision{} (F1 \detectorFOne). For \detectorHitFive{} of
covered sections, a covering human section is among its top five suggestions, and for
\detectorHitOne{} it ranks first. Larger embedding models bring no improvement. A plausible reason
is that an agent file and the human documents of the same project share their vocabulary, such as
command names, file paths and tool names, which favours lexical matching.

\paragraph{Grading partial coverage is harder.} Macro F1 over the three classes is
\detectorMacroFOne. Whether a section is fully shared depends on whether every one of its rules is
present, which a similarity score captures only approximately.

\paragraph{Error analysis.}
\ifdefined\detectorFalseAgentOnly
Most errors are covered sections flagged as agent-only (\detectorFalseAgentOnly) rather than missed
agent-only sections (\detectorMissedAgentOnly). False alarms are typically partially covered

summary phrased differently or a build command explained in prose; the ranked suggestions make them

with ranked suggestions matters more than precision.

\section{Discussion}\label{sec:discussion}
%======================================================================

\paragraph{Projects onboard their agents better than their people.} The knowledge that newcomers
find hardest to obtain, namely the development process, the environment, the code structure and
its pitfalls, is documented in most of the studied repositories, but in the file addressed to the
agent. Three factors may explain this. First, an agent cannot ask a maintainer, so everything it
needs must be written down, whereas a human newcomer is expected to read the code, ask on the
issue tracker or learn by doing. Second, writing for an agent pays off immediately: an instruction
that prevents a wrong command helps in the next session, while the benefit of human documentation
is delayed and diffuse. Third, tools such as Claude Code's \texttt{/init} generate an initial agent
file from the code, and no equivalent exists for CONTRIBUTING files.

\paragraph{Implications for maintainers.} Much of the effort of improving onboarding documentation
has already been spent. Agent-only sections on building, testing, the environment and the
architecture can be moved or adapted into CONTRIBUTING, and a lexical detector suffices to find
them: with recall \detectorRecall{} and ranked suggestions, \texttt{gapcheck} reduces the
comparison to a short review. Copying alone is insufficient, however. Agent files are terser and
harder to read than CONTRIBUTING files (Flesch \agentFlesch{} against \contribFlesch), and
instructions about the agent's own tools and behaviour are irrelevant to a person. Alternatively,
maintainers can avoid duplication by keeping shared knowledge in one human-readable document and
pointing the agent file to it, as some projects already do.

\paragraph{Keeping two documents consistent.} The \nConflictUnits{} contradictions show that two
parallel documents drift apart. A detector run in continuous integration could flag new agent-only
knowledge and possible contradictions whenever either file changes, in line with prior work on
detecting documentation issues~\cite{aghajani2019issues}.

\paragraph{Implications for tool builders.} Agent vendors shape what maintainers write: they define
the file names, generate first drafts and recommend content. Their tools could also propose
matching updates to CONTRIBUTING, or read the human documentation first and generate only what is
specific to the agent. A shared format such as \texttt{AGENTS.md} would simplify this.

\paragraph{Implications for researchers.} Agent files make explicit project knowledge that
onboarding research has so far elicited through interviews and
observation~\cite{dagenais2010landscape,steinmacher2015social}. They reveal what maintainers
consider necessary to work on their project, which our results show to be mainly process and
environment knowledge.

\section{Limitations and Threats to Validity}\label{sec:limitations}
%======================================================================

\paragraph{Construct validity.} We compare agent files with README and CONTRIBUTING only. Projects
also document themselves in wikis, on websites and in \path{docs/} folders, and knowledge found
only there counts as agent-only. The \path{docs/} check bounds this for documents in the repository
and the links out analysis for external pointers, but neither covers websites. Coverage is a
judgement about knowledge rather than text; the codebook's rules make it repeatable, but the
boundary between partial and shared coverage remains the main source of disagreement
(Table~\ref{tab:rel}). Needs and barriers were labelled from the text rather than observed in
newcomers, so they describe which needs the knowledge would serve.

\paragraph{Internal validity.} \nDraftsReviewed{} of the \nCodedUnits{} labels started from an LLM
draft that the author reviewed and kept in \draftKeepRate{} of cases, so the labels may inherit the
drafting model's judgement. The \nDraftsCorrected{} corrections show that drafts were sometimes
wrong, but cannot reveal how many wrong drafts went unnoticed. The blind reliability set yields a
lower agent-only share than the drafted sets (\agentOnlyBlind{} against \agentOnlyDrafted;
Table~\ref{tab:sens}), which may reflect the drafts, the different repositories, or both. The main
estimate should therefore be read together with the blind estimate.
\ifsecondcoder\ifsecondcoderllm
Agreement on that set was measured against an LLM annotator, which may share blind spots with the
drafting model; agreement between two human coders was not measured. The \nNeedFromSecond{} need
labels taken from this annotator carry the same caveat.
\fi\else
Coverage labels come from a single annotator; agreement with a second annotator is pending.
\fi
Finally, fork and archive status reflect the present state of each repository, not its state at
the snapshot commit.

\paragraph{External validity.} Requiring a CONTRIBUTING file removes most repositories and selects
larger, more established projects (median \sampleMedianStars{} stars). Smaller projects, most of
which lack a CONTRIBUTING file, may show an even larger gap. The study covers three English file
types from one dataset, collected between \snapshotFirst{} and \snapshotLast; these files change
quickly, and other agents, such as Cursor with its rule files, may differ. Mining GitHub carries
known risks~\cite{kalliamvakou2014perils}, which we mitigated by excluding forks, archived
repositories, copies and files that only link elsewhere.

\paragraph{Conclusion validity.} Sections are nested in repositories. We therefore estimate at the
repository level, resample whole repositories and use clustered models. With \geeNTerms{}
regression terms, some significant odds ratios may arise by chance; after a Bonferroni correction,
\geeBonferroniCats{} remain significant. The detector's thresholds were tuned on only
\detectorNDev{} sections; the replication package reports bootstrap confidence intervals for all test results.

%======================================================================
\section{Conclusion and Future Work}\label{sec:conclusion}
%======================================================================

Coding agents and human newcomers need the same project knowledge, but they read different
documents. This paper compared agent context files with the README and CONTRIBUTING of the same
commit in \nSampleRepos{} repositories. On average, \agentOnlyOverall{} of agent file knowledge is
absent from the human documentation (\agentOnlyBlind{} in the blind labelled repositories), and
\anyGapOverall{} is not fully available to people. The gap appears in most repositories and in all
three file types, and it concerns how to work on the project: the development process, the
environment, and the architecture and its pitfalls. Because this knowledge already exists in the
repository, a lexical detector can locate most of it with high recall, giving maintainers a direct
way to improve their contributor documentation.

Three directions remain open. First, a second human annotator should label the reliability set to
measure agreement between people\ifsecondcoderllm, which this study measured only between a person
and an LLM\fi. Second, a controlled study should test whether moving agent-only knowledge into
CONTRIBUTING improves the success of first contributions. Third, a longitudinal study should track
whether the gap grows or shrinks as agent files and human documents evolve.
