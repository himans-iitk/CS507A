\title{What We Tell the Agent but Not the Newcomer}
\subtitle{Mining Agent Context Files for Gaps in Human Onboarding Documentation}

\author{Himanshu Mishra}
\affiliation{\institution{University of British Columbia}\city{Vancouver}\country{Canada}}
\email{himishra@student.ubc.ca}

\begin{abstract}
AI coding agents read repository context files, or \emph{agent files}, for instructions on how to
build, test and change a project. New contributors need much of the same guidance. How much of it
can they find in the README and CONTRIBUTING at the same commit? We sampled \nSampleRepos{} GitHub
repositories with all three files and labelled \nQueued{} agent-file sections. For
\draftedLabelShare{} of these sections, the author reviewed labels drafted by a large language
model. Among sections that convey project knowledge, the README and CONTRIBUTING omit the content
of \agentOnlyOverall{} and fully cover \sharedOverall{}, on average per repository. Of the sections
with missing or partial coverage, \needGroupTopShare{} address newcomer needs related to processes
and practices, especially the development workflow and environment. A lexical matcher based on
term frequency and inverse document frequency (TF-IDF) identifies sections absent from both
documents with an F1 score of \detectorFOne{} in held-out repositories.
\end{abstract}

\section{Introduction}
%======================================================================

Before making a first change, a newcomer to a software project has to work out how the code is
organised, how to set up a working environment, and which commands build and test the
project~\cite{sim1998rampup,begel2008novice,dagenais2010landscape}. In open source, mentors are
rarely available, and newcomers who encounter barriers often give up before their first
contribution~\cite{steinmacher2015social,steinmacher2015barriers}. The barriers they report include
missing knowledge of the project's process, problems with the local environment, and difficulty
finding their way in the code~\cite{steinmacher2015barriers,steinmacher2015social}. Projects address
these barriers mainly through a README that explains what the project is and a CONTRIBUTING file
that explains how to work on it~\cite{prana2019readme,steinmacher2019letmein}.

Projects now also write documentation for a second kind of newcomer. AI coding agents such as
Claude Code, OpenAI Codex and GitHub Copilot load a context file into every session:
\texttt{CLAUDE.md}, \texttt{AGENTS.md} or \path{.github/copilot-instructions.md} (Copilot for
short)~\cite{chatlatanagulchai2026agentreadmes,mohsenimofidi2026context}. We call these
\emph{agent files}. An agent starts in the same position as a human newcomer: it knows the
programming language but not the project. Maintainers therefore tell it how to build and test, how
the code is organised, which conventions to follow and which files not to touch. Whether such files
help agents is debated~\cite{gloaguen2026agentsmd}; we use them only as a record of what maintainers
consider necessary to work on their project, and ask whether the same record exists for people.

\paragraph{Motivation.} Three observations motivate this study.
\begin{enumerate}
\item \emph{Human onboarding documents are incomplete.} In a study of CONTRIBUTING files, 52\% of
projects omitted at least three of six common newcomer barriers~\cite{fronchetti2023contributing}.
\item \emph{Many projects have an agent file but no CONTRIBUTING file} (our sample). Of the
\nWithReadme{} agent files that pass our screening and whose repository has a README, only
\withContributingShare{} come with a CONTRIBUTING file. The other \withoutContributingShare{} have
no CONTRIBUTING file, so of their README and agent file, only the agent file is written for someone
who will change the code; such projects may still document this elsewhere, for example in a
\path{docs/} folder.
\item \emph{Where a CONTRIBUTING file exists, the agent file is often longer} (our sample). The
agent file is longer than CONTRIBUTING in \agentLongerShare{} of our sampled repositories (median
\agentWords{} against \contribWords{} words).
\end{enumerate}

Figure~\ref{fig:overview}, which Section~\ref{sec:method} uses as a running example, shows a case
from our data. The \texttt{AGENTS.md} of \path{microsoft/generative-ai-with-javascript} tells the
agent to install Node.js 20 or later, set a \texttt{GITHUB\_TOKEN} variable, and run
\texttt{npm install} and \texttt{npm start}. Neither the README nor the CONTRIBUTING file of the
same commit gives these setup steps, so a human newcomer must find them elsewhere or discover them
alone. If such cases are common, agent files contain knowledge that README and CONTRIBUTING omit,
and the agent file may be a source of material for improving them.

\input{figures/overview}

Prior studies examined agent files in
isolation~\cite{chatlatanagulchai2026agentreadmes,mohsenimofidi2026context,gloaguen2026agentsmd}
and onboarding documents in isolation~\cite{prana2019readme,fronchetti2023contributing}. To our
knowledge, no study has measured how much of what maintainers write for agents also appears, within
the same repository, in the files written for people. We address three research questions (RQs):

\begin{itemize}
\item \textbf{RQ1:} How much of the knowledge in agent files is absent from the README and
CONTRIBUTING of the same commit?
\item \textbf{RQ2:} Which newcomer needs and onboarding barriers does the knowledge that is absent
or only partially covered address? This question is descriptive: it characterises the gap rather
than comparing it with covered knowledge.
\item \textbf{RQ3:} How accurately can agent-only sections be detected automatically?
\end{itemize}

To answer them, we start from the Agent READMEs dataset~\cite{chatlatanagulchai2026agentreadmes}
and take each agent file together with the README and CONTRIBUTING of the same commit. We sample
\nSampleRepos{} repositories, \nPerAgent{} per file type, and split all three files at their
headings into \nUnits{} sections. We label \nQueued{} agent-file sections, using author-reviewed
drafts. The codebook combines a taxonomy of agent
instructions~\cite{chatlatanagulchai2026agentreadmes}, a coverage scale, the newcomer landscape of
Dagenais et al.~\cite{dagenais2010landscape} and the onboarding barriers of Steinmacher et
al.~\cite{steinmacher2015barriers}. Finally, we evaluate one lexical and three embedding matchers
that predict the coverage label from the files alone.

\begin{tcolorbox}[colback=black!3,colframe=black!35,boxrule=0.4pt,arc=1pt,left=4pt,right=4pt,top=3pt,bottom=3pt]
\small\textbf{Key findings.}
\begin{itemize}\setlength{\itemsep}{1pt}\setlength{\topsep}{2pt}\setlength{\leftmargin}{1em}
\item \textbf{RQ1:} Among agent-file sections that convey project knowledge, the mean share per
repository is \agentOnlyOverall{} for sections absent from both README and CONTRIBUTING and
\sharedOverall{} for sections fully covered.
\item \textbf{RQ2:} \needGroupTopShare{} of gap sections (agent-only or partially covered) serve
\emph{\needGroupTop} needs. The barrier these sections could most often ease is
\emph{\barrierTopOne}.
\item \textbf{RQ3:} TF-IDF detects agent-only sections with F1 \detectorFOne{} (recall
\detectorRecall, precision \detectorPrecision), against \baselineFOne{} for labelling every section
agent-only. TF-IDF has the highest observed F1 of the four matchers on this task.
\end{itemize}
\end{tcolorbox}

\noindent This paper makes the following contributions:
\begin{itemize}
\item To our knowledge, the first comparison of agent files with the README and CONTRIBUTING of the
same repository and commit, at section level, with population estimates for three agent-file types.
\item A description of the knowledge that README and CONTRIBUTING omit or only partially cover, in
terms of established models of newcomer needs and onboarding barriers.
\item A lexical matcher for agent-only sections, evaluated on repositories not used for tuning, and
released as \texttt{gapcheck} in a per-repository variant that was not evaluated separately.
\item A corpus of repository snapshots with a codebook and tools for labelling sections and
analysing documentation coverage.
\end{itemize}

\section{Related Work}\label{sec:related}
%======================================================================

\subsection{Coding agents and context files}

Large language models (LLMs) now support many software engineering
activities~\cite{hou2024llm4se}. Coding agents go beyond code completion: they explore a
repository, run commands and submit changes on their own. Benchmarks such as SWE-bench measure how
well they resolve real GitHub issues~\cite{jimenez2024swebench}, and the design of an agent's tools
strongly affects its success~\cite{yang2024sweagent}. Developers report that AI assistants often
miss their requirements and are hard to steer~\cite{liang2024usability}. Context files are one
response to this problem. They are Markdown files, loaded into every session, in which maintainers
describe the project for the agent.

Chatlatanagulchai et al.\ collected \nPackageFiles{} agent files
from GitHub, grouped their instructions into 16 categories, and found them hard to
read~\cite{chatlatanagulchai2026agentreadmes}. Mohsenimofidi et al.\ studied how open source
projects engineer the context they give AI agents~\cite{mohsenimofidi2026context}. Gloaguen et al.\
evaluated whether \texttt{AGENTS.md} files help coding agents resolve tasks. They found that such
files often do not improve task success and can lower it, while increasing cost. They recommend that
the files state only minimal requirements, such as tooling specific to the
project~\cite{gloaguen2026agentsmd}. These results caution against assuming that agent files make
agents better. Our study does not rely on that assumption, because it uses the agent file only as a
record of the knowledge that maintainers chose to write down. All three studies treat the agent
file in isolation; this study relates it to the documentation that the same project writes for
people. We reuse the dataset and the 16 categories of Chatlatanagulchai et al.

\subsection{Newcomer onboarding}

Onboarding has long been recognised as a problem. Sim and Holt described how new developers, whom
they called ``software immigrants'', settle into a project~\cite{sim1998rampup}. Begel and Simon
observed new hires who had to learn their team's tools and processes before they could
contribute~\cite{begel2008novice}, and Ko et al.\ catalogued the information needs of developers in
teams~\cite{ko2007information}. Dagenais et al.\ described the \emph{landscape} that newcomers must
learn~\cite{dagenais2010landscape}. It covers the product (architecture, design, technologies,
domain), processes and practices (development and task processes, environment and tools,
configuration management), the team, the documentation, and the wider context.

For open source, Steinmacher et al.\ consolidated the barriers that newcomers face, including
orientation problems, gaps in the newcomers' own knowledge, documentation problems and technical
hurdles~\cite{steinmacher2015barriers,steinmacher2015social}. They also built a portal that lowered
these barriers~\cite{steinmacher2016portal} and derived guidelines for
maintainers~\cite{steinmacher2019letmein}. Santos et al.\ review the onboarding tools proposed since
then~\cite{santos2024onboarding}, and Tan et al.\ studied ``good first issues'' as a way to help
newcomers choose a task~\cite{tan2020goodfirst}. Closest to our work, Fronchetti et al.\ checked
CONTRIBUTING files against the barrier model and found that most projects leave several barriers
unaddressed~\cite{fronchetti2023contributing}. While they asked which barriers CONTRIBUTING files
omit, we ask which barriers a project already addresses in writing, but only for its agent. We use
the landscape of Dagenais et al.\ and the barriers of Steinmacher et al.\ to classify this
knowledge.

\subsection{Developer documentation}

Developers rely on documentation but often find it incomplete or
outdated~\cite{lethbridge2003documentation,aghajani2019issues,aghajani2020practitioners}, and poor
documentation is a major obstacle to learning an API~\cite{robillard2009apis}. Prana et al.\
classified the content of GitHub READMEs and found that they mostly describe what a project is and
how to use it, and less often how to contribute~\cite{prana2019readme}. Elazhary et al.\ showed that
the actual contribution process of many projects diverges from their CONTRIBUTING
guidelines~\cite{elazhary2019guidelines}. Documentation can also be improved from external sources,
for example by adding insights from Stack Overflow to API documentation~\cite{treude2016augmenting}.
In contrast to such external sources, the agent file is written by the project's own maintainers
and already sits in the repository.

\subsection{Document matching and LLM-assisted labelling}

Deciding whether one text covers another is a long-standing information retrieval task in software
engineering. Traceability recovery links documentation to code with TF-IDF and vector space
models~\cite{antoniol2002traceability,salton1988termweighting} or latent semantic
indexing~\cite{marcus2003lsi}, and sentence embeddings are now the common choice for semantic
similarity~\cite{reimers2019sbert}. We compare both families on a new task: matching agent
instructions to sections of README and CONTRIBUTING.

LLMs are increasingly used to label text. They match or exceed crowd workers on some annotation
tasks~\cite{gilardi2023chatgpt}. In software engineering, they can replace part but not all of the
human effort, and agreement between models indicates which tasks are
suitable~\cite{ahmed2025llmannotation}. LLMs also serve as judges of other models'
output~\cite{zheng2023judge}. In this study, a model drafted labels for author review and filled
some fields that were empty after review. Section~\ref{sec:labelling} describes how each field was
labelled, and Section~\ref{sec:limitations} discusses how the drafts could affect the estimates.

\section{Methodology}\label{sec:method}
%======================================================================

Figure~\ref{fig:overview} gives an overview of the pipeline. The top row lists the six stages; the
bottom row traces one real section through every stage and serves as a running example in this
section.

\subsection{Data source and snapshot commit}

The study builds on the Agent READMEs dataset~\cite{chatlatanagulchai2026agentreadmes}. It contains
\nPackageFiles{} agent files from \nPackageRepos{} GitHub repositories: \texttt{CLAUDE.md} and
\texttt{AGENTS.md} in the repository root, and \texttt{copilot-instructions.md} in \path{.github/}.
For each file, the dataset stores the content and a git hash. We found that this hash identifies
the file content (a git blob) rather than a commit. To compare the files as they stood together, we
recover the \emph{snapshot commit}: the newest commit in the agent file's history at which the file
has exactly that content. We search the dataset's commit history first and the GitHub API as a
fallback; \nSnapshotPackage{} sampled snapshots come from the dataset and \nSnapshotAPI{} from the
API. The snapshots date from \snapshotFirst{} to \snapshotLast. At each snapshot commit, we locate
the README and CONTRIBUTING the way GitHub does: in \path{.github/}, then the root, then
\path{docs/}. We verify every downloaded file against its git blob hash: the agent file against the
hash in the dataset, and README and CONTRIBUTING against the hashes in the snapshot commit's tree.
The corpus can therefore be rebuilt exactly.

\subsection{Filtering and sampling}\label{sec:sampling}

Table~\ref{tab:flow} lists the filtering steps, applied in the order shown. Besides removing
deleted, forked and archived repositories and files whose snapshot commit could not be found, we
removed agent files that are symbolic links, that only point to another file (for example, a
\texttt{CLAUDE.md} containing only \texttt{@AGENTS.md}), that are not in English, or that copy
another repository's agent file (TF-IDF cosine similarity of at least 0.9). The
\nDuplicateDropped{} copies were mostly tool-installed rule packs and mirrored
projects~\cite{hata2021metamaintenance}. Finally, we required a README and a CONTRIBUTING file at the
snapshot commit. This step removed \nDroppedNoContributing{} files, more than all other steps
together, and left \nEligible{} eligible files. All estimates in this paper refer to this
population: agent files of the three types in the Agent READMEs dataset whose repository has a
README and a CONTRIBUTING file.

\input{tables/flow}

We sampled \nPerAgent{} files per file type (random seed 507), giving each type the same sample
size. We drew at most one file per repository, because \nMultiAgentRepos{} repositories in the
dataset have more than one agent file and repeated repositories would not be independent. The
sampled repositories are larger than is typical in the dataset: their median is
\sampleMedianStars{} stars, against \eligibleMedianStars{} for eligible repositories and
\datasetMedianStars{} for all repositories in the dataset. Because the three types are not equally
common among eligible files (\nEligibleCopilot{} Copilot, \nEligibleClaude{} \texttt{CLAUDE.md},
\nEligibleAgents{} \texttt{AGENTS.md}), overall estimates weight each type by its share of eligible
files. We flagged two subsets for robustness checks: \nInitUnedited{} \texttt{CLAUDE.md} files that
still carry the header of Claude Code's \texttt{/init} command and were never edited, and
\nStubContributing{} CONTRIBUTING files with fewer than 50 words.

\subsection{Sections}\label{sec:sections}

A whole file is too coarse to show what is missing, and a single sentence is too fine to hold a rule
together with its context. We therefore split every file at its headings into \emph{sections}:
second- and third-level headings, and first-level headings where a file uses several of them as
section titles. Text before the first heading forms its own section, and files without headings are
split into top-level blocks. Headings inside code blocks are ignored, and tables of contents are
removed. We call the sections of README and CONTRIBUTING \emph{human sections}. The
median agent-file section has \agentUnitMedianWords{} words, and the median repository has
\agentUnitsPerRepoMedian{} agent-file sections (90th percentile \agentUnitsPerRepoNinety, maximum
\agentUnitsPerRepoMax) and \humanSectionsPerRepoMedian{} human sections.

\subsection{Codebook}\label{sec:codebook}

Table~\ref{tab:codebook} gives the codebook. Each agent-file section receives four labels. Its
\emph{categories} are any of the 16 instruction categories of Chatlatanagulchai et
al.~\cite{chatlatanagulchai2026agentreadmes}. Its \emph{coverage} states whether the README and
CONTRIBUTING of the same commit contain its knowledge: the section is \emph{agent-only},
\emph{partially covered} or \emph{shared}, or \emph{agent-directed} if it only addresses the AI (for
example, ``be concise''). Agent-directed sections are excluded from all coverage results; we call the
remaining sections \emph{knowledge sections}, and agent-only and partially covered sections
together \emph{gap sections}. For gap sections only, the \emph{need} is the feature of the newcomer
landscape of Dagenais et al.~\cite{dagenais2010landscape} that the knowledge serves, and the
\emph{barriers} are those of Steinmacher et al.~\cite{steinmacher2015barriers,santos2024onboarding}
that it could ease if it were in README or CONTRIBUTING. Two flags mark special cases:
\emph{conflict}, when README or CONTRIBUTING contradicts the section, and \emph{links out}, when they
only point elsewhere for its topic. Category, need and barrier names are kept as in their sources.
Because the category \textsc{Development Process} and the need \emph{Development Process} are
different constructs, we write categories in small capitals and needs in italics.

Coverage is judged on knowledge rather than wording, by three rules. First, a paraphrase counts as
coverage, but a link to a website or wiki does not. Second, the boundary between agent-only and
partially covered is whether README or CONTRIBUTING states at least one of the section's facts,
commands or rules, possibly in a less specific form. If so, the section is partially covered: a
CONTRIBUTING file that says ``run the tests before opening a pull request'' partially covers a
section that requires \texttt{make test-unit -race} before every pull request. If they only name the
topic, for example with a heading ``Testing'' or a remark that the project has tests, without
stating any of the section's facts or rules, the section is agent-only. Third, a section is shared
only if every fact, command and rule in it is present. A section that mixes agent-directed sentences
with project knowledge is labelled by its project knowledge. In the running example
(Figure~\ref{fig:overview}), neither file mentions Node.js or \texttt{GITHUB\_TOKEN}, so the section
is agent-only; it serves the need \emph{Development Environment and Tools} and could ease the barrier
\emph{Local environment setup hurdles}.

\subsection{Labelling procedure}\label{sec:labelling}

The labelling tool displayed each agent-file section beside the full README and CONTRIBUTING.
Annotators could mark the passages that covered the section. The tool hid all matcher scores and
rankings. We used the pilot set (\nPilotRepos{} repositories, \nPilotUnits{} sections) to refine
the codebook and tune the detector. The author reviewed model-drafted labels
for the sections from the main-set repositories. The author and a second human
annotator independently assigned coverage and instruction categories from the documents without
model drafts. The analyses use the author's final coverage and category labels from all three sets.

\subsection{Analysis for RQ1 and RQ2}\label{sec:analysis}

\paragraph{Labelled sections and estimands.} To bound the labelling effort, we labelled up to 10
randomly chosen sections per agent file, for a total of \nQueued{}. This covered every section in
\nFullyCodedRepos{} repositories. After excluding agent-directed sections, the coverage analysis
uses \nKnowledgeUnits{} knowledge sections from \nRepoKnowledge{} repositories. The other
\nReposNoKnowledge{} repositories contributed only agent-directed sections to the labelled sample.
We report two kinds of estimates. \emph{Repository-level} results (Tables~\ref{tab:rq1} and~\ref{tab:sens},
Figure~\ref{fig:repos}) average each repository's shares, so every repository counts once within its
file type. Because sections were chosen at random within each repository, the cap does not bias the
repository mean, although it increases its variance. \emph{Section-level} results
(Tables~\ref{tab:rq1cat}, \ref{tab:rq2needs} and~\ref{tab:rq2bar}) pool sections and weight each by
the number of eligible sections in its repository divided by the number labelled, so that they
represent all sections of the sampled files. In both, a section counts the same whatever its
length.

\paragraph{Coverage estimates.} For each repository, we compute the share of its knowledge sections
in each coverage class and average these shares over the repositories of each file type. The overall
estimate weights the three types by their share of eligible files. We report 95\% confidence
intervals from 1{,}000 bootstrap samples that resample repositories within each file
type~\cite{efron1993bootstrap}.

\paragraph{Categories and file types.} Sections of the same repository are correlated, so tests that
treat sections as independent would overstate significance. We therefore fit a logistic regression
for agent-only with indicators for each category and the file type, estimated with generalised
estimating equations (GEE) clustered by repository~\cite{liang1986gee}. Each category is compared
with all sections that lack it, holding the other categories and the file type constant. With
\geeNTerms{} terms (16 categories and 2 file-type indicators), we report which effects survive a
Bonferroni correction ($p < \geeBonferroniAlpha$) and treat the others as exploratory.

\paragraph{Needs and barriers.} For RQ2, we report the weighted distribution of needs (one per gap
section) and barriers (any number per gap section). Because needs and barriers were labelled only
for gap sections, RQ2 describes the knowledge in the gap; it cannot show whether some kinds of
knowledge are missing more often than others.

\paragraph{Robustness.} We repeat the coverage analysis with three separate exclusions. We omit
unedited \texttt{/init} files, CONTRIBUTING files with fewer than 50 words, or sections whose
topic README and CONTRIBUTING address only through a link. We also estimate how often other
documentation in the repository matches agent-only sections. For a random subsample (seed 507) of \nDocsSubsample{} of the
\nDocsRepos{} sampled repositories with Markdown files in \path{docs/}, the RQ3 detector compares
agent-only sections against README, CONTRIBUTING and \path{docs/} together.

\subsection{Gap detector for RQ3}\label{sec:detector}

\paragraph{Items.} An agent-file section often contains several rules, of which only some may be
covered. The detector therefore splits each section into \emph{items} (list entries, sentences and
code blocks), giving \nItemsAgent{} agent items and \nItemsHuman{} human items. Short items also fit
within the input limits of embedding models.

\paragraph{Matchers.} We compare one lexical matcher with three embedding models. The lexical
matcher uses TF-IDF over words and word pairs~\cite{salton1988termweighting}, with document
frequencies computed on all files of the corpus, including those of the test repositories; this step
uses no labels. The embedding models increase in size: all-MiniLM-L6-v2 (23 million
parameters)~\cite{reimers2019sbert}, bge-base-en-v1.5 (109 million)~\cite{xiao2023cpack} and
Qwen3-Embedding-0.6B (596 million)~\cite{zhang2025qwen3embedding}. Each matcher compares an
agent-file section only with the human sections of its own repository and computes three scores:
\emph{unit max}, the best similarity between the whole section and any whole human section;
\emph{item mean}, the mean over items of each item's best match; and \emph{item cov@$\tau$}, the
share of items whose best match exceeds a threshold $\tau$. The matcher also ranks the human
sections, which shows a maintainer where a match comes from. Figure~\ref{fig:overview} shows these
scores for the running example: none of its four items has a close match, so its item mean falls
below the threshold and the section is predicted agent-only. Rank correlations of item mean between
matchers range from \matcherRhoMin{} to \matcherRhoMax, so the matchers rank sections similarly but
not identically.

\paragraph{Evaluation protocol.} The primary task is binary: is a section agent-only? The
\nPilotRepos{} pilot repositories form the development set and the remaining repositories the test
set, so no repository appears in both. Agent-directed sections are excluded, which leaves
\detectorNDev{} of the \nPilotUnits{} pilot sections for development and \detectorNTest{} sections
for testing. On the development set only, we select each matcher's score, the threshold that
maximises F1 for agent-only, two further thresholds for a three-class prediction (agent-only,
partially covered, shared), and the matcher to release. On the test set, we report precision,
recall and F1 for agent-only; the area under the receiver operating characteristic curve (AUC);
macro F1 over the three classes; and how often a human section marked as covering is ranked first
(hit@1) or among the top five (hit@5). As a baseline, we label every section agent-only; its
precision equals the share of agent-only sections in the test set. We use a single split and report
repository-bootstrap intervals for F1 and AUC.

\paragraph{Released tool.} \texttt{gapcheck} applies the selected matcher and thresholds to a single
checkout. With TF-IDF, it computes document frequencies on that repository alone, so its scores are
not on exactly the scale of the evaluated configuration (Section~\ref{sec:limitations}).

\subsection{Implementation}

The pipeline is written in Python. It parses Markdown with markdown-it-py, fits the regression with
statsmodels, computes readability with textstat, and computes embeddings with sentence-transformers
on a single GPU. The pipeline caches responses from the GitHub API and uses fixed random seeds for
sampling and resampling. The analyses take the final section labels as input.

\paragraph{Few knowledge sections are fully covered by README and CONTRIBUTING.}
Table~\ref{tab:rq1} reports mean shares per repository for the \nKnowledgeUnits{} labelled sections

\subsection{Robustness of the RQ1 estimate}\label{sec:robustness}

\input{tables/sensitivity}

\paragraph{Sensitivity to document and section exclusions.} The estimated agent-only share ranges
from \sensLow{} to \sensHigh{} across the three exclusions, compared with \agentOnlyOverall{}
in the primary analysis (Table~\ref{tab:sens}). Excluding sections for which the human documents
only link elsewhere gives the lowest estimate. Excluding unedited \texttt{/init} files gives the
highest.

\paragraph{Other files may close part of the gap.} Of the \nDocsSubsampleFetched{} repositories in
the \path{docs/} subsample, \docsCheckRepos{} have at least one labelled agent-only section. In
these, the detector matches \docsCheckCovered{} of \docsCheckUnits{} agent-only sections
(\docsCheckShare) to a \path{docs/} section. This automatic, unverified match rate suggests that the
choice of README and CONTRIBUTING as the comparison matters; it does not measure how much
(Section~\ref{sec:limitations}). All our estimates refer to README and CONTRIBUTING only.

\paragraph{README or CONTRIBUTING sometimes contradicts the agent file.} In \nConflictUnits{} of the
\nKnowledgeUnits{} knowledge sections (\conflictShare), README or CONTRIBUTING contradicts the agent
file, for example by naming a different test command, package manager or tool version. One of the
two files is then outdated, wrong, or written for a different context, such as continuous
integration rather than a local machine, and a newcomer who follows CONTRIBUTING may fail where the
agent succeeds. In a further \nLinksOutUnits{} sections, README or CONTRIBUTING only points to a
website or wiki for the topic; the coverage label does not count such pointers.

\paragraph{Error analysis.} Most errors are covered sections flagged as agent-only

rule itself, for example lists of commands for the same tool (\texttt{mise run lint},
\texttt{bun test}) whose specific subcommands never appear for humans.

\section{Discussion}\label{sec:discussion}
%======================================================================

\paragraph{Agent files hold knowledge that README and CONTRIBUTING omit.} In most studied
repositories, knowledge about the development process, the environment and the code structure is
written in the file addressed to the agent but not, or only partially, in README and CONTRIBUTING.
First, an agent cannot ask a maintainer, so everything it needs must be
written down, whereas a human newcomer is expected to read the code, ask on the issue tracker or
learn by doing. Second, writing for an agent may pay off immediately: an instruction that prevents a
wrong command helps in the next session, while the benefit of contributor documentation is delayed and
diffuse. Third, tools such as Claude Code's \texttt{/init} generate an initial agent file from the
code, and no equivalent exists for CONTRIBUTING files. Excluding unedited \texttt{/init} files
hardly changes the estimate (Table~\ref{tab:sens}), but edited \texttt{/init} files remain in the
sample, so this does not test the hypothesis.

\paragraph{Implications for maintainers.} Agent-only sections on building, testing, the environment
and the architecture may be worth adapting into CONTRIBUTING, after checking that they are correct
and current: agent files can be generated, aspirational or stale, and the \nConflictUnits{}
contradictions (Section~\ref{sec:robustness}) show that one of two files is sometimes wrong. A
lexical matcher can help find candidates. In the evaluated configuration, it finds most agent-only
sections (recall \detectorRecall) and ranks candidate human sections; at precision
\detectorPrecision, about three in ten flagged sections are already covered. Copying alone is
insufficient: agent files are written as terse lists rather than prose, and instructions about the
agent's own tools and behaviour are irrelevant to a person. Alternatively, maintainers can keep
shared knowledge in one human-readable document and point the agent file to it. The dataset contains
\nLinkOnlyFiles{} agent files that consist only of a pointer to another file; we excluded them
(Section~\ref{sec:sampling}).

\paragraph{Keeping two files consistent.} The \nConflictUnits{} contradictions show that parallel
files can drift apart. A matcher run in continuous integration could flag new agent-only sections
and possible contradictions whenever either file changes, in line with prior work on detecting
documentation issues~\cite{aghajani2019issues}.

\paragraph{Implications for tool builders.} Agent vendors shape what maintainers write: they define
the file names, generate first drafts and recommend content. Their tools could also propose matching
updates to CONTRIBUTING, or read README and CONTRIBUTING first and generate only what is specific to
the agent. A shared format such as \texttt{AGENTS.md} would simplify such tools.

\paragraph{Implications for researchers.} Agent files make explicit project knowledge that
onboarding research has so far elicited through interviews and
observation~\cite{dagenais2010landscape,steinmacher2015social}. They reveal what maintainers
consider necessary to work on their project, which in our data is mainly process and environment
knowledge.

\section{Limitations and Threats to Validity}\label{sec:limitations}
%======================================================================

\paragraph{Construct validity.} We compare agent files with README and CONTRIBUTING only. Projects
also document themselves in other files such as \texttt{DEVELOPMENT.md}, in \path{docs/} folders, in
wikis and on websites, and knowledge found only there counts as agent-only. The \path{docs/} check
(Section~\ref{sec:robustness}) suggests that this matters, but its matches were not verified by hand,
we have no reference rate for how often the detector matches sections that are absent from all
files, its TF-IDF document frequencies are computed on each repository alone, and websites are not
covered. Each section contributes one coverage judgement regardless of its length or number of
instructions. When a section gives several rules, documenting even one of them can move it from
agent-only to partially covered (Section~\ref{sec:codebook}). The estimate therefore depends in
part on what the annotator accepts as a paraphrase of a rule. Need and barrier labels describe how
the guidance could help a newcomer. Its accuracy, currency and effect on contributors remain open
questions.

% \paragraph{Internal validity.} The author retained the proposed coverage label for \draftKeepRate{}
% of the \nDraftsReviewed{} sections that began with an LLM draft. Some errors in those drafts may
% have survived review. Each repository followed one labelling procedure, so the pooled estimate
% cannot isolate the influence of seeing a draft. For RQ2, each gap section has a single assessment
% of newcomer needs and barriers, and the model filled those fields directly for
% \needModelOnlyShare{} of gap sections. About three quarters of the RQ3 test labels also came from
% reviewed drafts. TF-IDF document frequencies were computed on all files including
% the test repositories, without using labels. The threshold was chosen to maximise F1 on the
% development set; we did not evaluate a recall-oriented threshold. We did not compute a
% random-ranking reference for hit@1 and hit@5, which therefore cannot be compared with chance. The
% released \texttt{gapcheck} computes document frequencies per repository and was not evaluated
% separately, so its behaviour may differ from the evaluated configuration. Finally, fork and archive
% status reflect the present state of each repository, not its state at the snapshot commit.

% \paragraph{External validity.} Requiring a CONTRIBUTING file removes most repositories and selects
% larger, more established projects (Section~\ref{sec:sampling}). The estimates hold for eligible files
% of one dataset; smaller projects, most of which lack a CONTRIBUTING file, may differ in either
% direction. Excluding the \nLinkOnlyFiles{} agent files that only point to another file may raise the
% estimate: where such a pointer leads to README or CONTRIBUTING, nothing in the agent file is
% agent-only. We did not check where these pointers lead. The study covers three English file types
% collected between \snapshotFirst{} and \snapshotLast; these files change quickly, and other agents,
% such as Cursor with its rule files, may differ. Mining GitHub carries known
% risks~\cite{kalliamvakou2014perils}, which we mitigated by excluding forks, archived repositories and
% copies.

\paragraph{Conclusion validity.} Sections are nested in repositories. We therefore estimate at the
repository level, resample whole repositories and use clustered models. With \geeNTerms{} regression
terms, some significant odds ratios may arise by chance; after a Bonferroni correction,
\geeBonferroniCats{} remain significant, and we treat the other effects as exploratory. Differences
between file types could be too small for this sample to detect. We tuned the detector's thresholds
on \detectorNDev{} sections and evaluated them on a single split. The reported differences between
matchers are descriptive.

\section{Conclusion and Future Work}\label{sec:conclusion}
%======================================================================

Coding agents and human newcomers need much of the same project knowledge, but they read different
files. This paper compared agent files with the README and CONTRIBUTING of the same commit in
\nSampleRepos{} repositories. Among agent-file sections that convey project knowledge,
\agentOnlyOverall{} are absent from both documents and \sharedOverall{} are fully covered, on
average per repository. Agent-only sections appear in all three file types. Gap sections most
often concern the development workflow and environment. On held-out repositories, a lexical
matcher finds most agent-only sections (recall \detectorRecall), giving maintainers a way to find
candidates for their contributor documentation.

Checking \path{docs/} folders and contributor websites by hand would show how much guidance
newcomers can already find elsewhere. Verifying commands and paths would help identify which
instructions are accurate enough to reuse. The detector should be compared with stronger
baselines, including BM25, overlap of commands and paths, and an LLM judge. Finally, a controlled
study should test whether moving agent-only knowledge into CONTRIBUTING helps first contributions,
and a longitudinal study should track whether the gap grows or shrinks as the files evolve.
