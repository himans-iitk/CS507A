## Decision 1 — can we fetch README/CONTRIBUTING at "the same commit"?

Not directly. `file_commit` is the file's **blob SHA** returned by the contents API on the branch
head (verified: it resolves via `git/blobs/`, not `git/commits/`; HF's `content_commit_sha` is the same value).

It is recoverable exactly: the commit that introduced that blob is the snapshot commit for the
agent file. In a 30-file pilot (10 per agent) the latest commit in the package history held the
stored blob in 25/30 cases; in the other cases the blob appears at an earlier commit of the same
file (checked on `espressif/esptool`). No repo or file had disappeared.

**Rule for Phase 2:** walk the file's commit history (package history first, API
`commits?path=` as fallback) and pick the commit whose version of the agent file has
`blob_sha`; fetch README and CONTRIBUTING at that commit. Interpretation: the human docs as they
stood when the maintainer wrote this version of the agent file. Log files where no commit matches.

Note for the proposal: say "the commit at which the agent file has the analysed content",
not "the snapshot commit", and mention that the dataset's `content_commit_sha` is a blob SHA.

## Decision 2 — can we reuse their 16-category labels?

Not as unit labels. Their labels are assigned to **whole files** (332 files: 118 Claude, 94 Codex,
120 Copilot; median 6 labels per file; agreement 80.3% before negotiated consensus). Our unit is
an H2/H3 section, so every unit still needs its own category.

What we can reuse:
- the 16-category taxonomy and its definitions and examples as our codebook dimension A;
- their files as a consistency check: the union of our unit labels for a file should cover its
  file-level labels (324 of the 332 labelled files are in the static dataset);
- their GPT-5 classification prompt (micro-F1 reported in the paper) as a starting point for
  pre-labelling units, with human verification.

Their prevalence table (reproduced exactly): Test 75.9%, Implementation Details 70.8%,
Architecture 68.1%, Development Process 65.1%, Build & Run 63.0%, System Overview 59.0%,
Maintainability 44.6%, Config & Environment 38.9%, Documentation 26.8%, Debugging 25.3%,
AI Integration 24.1%, DevOps 18.4%, Security 14.8%, Performance 14.5%, UI/UX 8.7%,
Project Management 5.4%.

## Other things to carry into Phase 2

- **Multi-file repos (347):** decide whether to sample by file or by repo. Sampling by repo and
  merging all agent files keeps units independent of tool choice; sampling by file keeps the
  per-agent strata clean. Recommended: stratify by file, exclude the second file of a repo already
  drawn, and keep the multi-tool repos as a flag.
- **Two content versions:** `raw_datasets/*_data_dump.csv` is an earlier crawl; 415 of 2,303 files
  differ from `static_content`. Use `static_content` (it has the blob SHA).
- Their sample filtered non-English files with `langdetect`; we should apply the same filter.
- The paper's inclusion criterion was ≥ 5 stars; median stars are 51–96, so many repos are small
  and may lack a CONTRIBUTING file — expect a large drop when requiring one.
